# Request Lab 편집 요청·응답의 프로젝트 저장 설계

상태: **목업·설계, 제품 미구현 / 사용자 승인 대기**. 현재 `FEAT/request-lab-ui`의 독립 요청 편집 UI를 유지한다. 이름뿐 아니라 각 편집 요청의 현재 REQ와 마지막 RES를 프로젝트에 보관한다. 저장은 HTTP 전송을 발생시키지 않는다.

## 화면과 동작

- 기존 Original·편집 요청 드롭다운·연필·×·+를 유지한다. 헤더 오른쪽에 프로젝트 이름과 작은 저장 상태만 추가한다. 요청·응답 안에 설명 행이나 전송 이력을 다시 넣지 않는다.
- 이름·REQ 편집은 잠시 입력을 멈추면 자동 저장한다. 요청 추가·삭제, 인증 적용, 마지막 RES 갱신도 저장 대상이다. **과거 응답 목록은 만들지 않는다.** REQ를 수정한 뒤에는 마지막 RES가 이전 요청의 결과임을 유지한다.
- 저장 상태는 `저장 대기 → 저장 중 → 프로젝트 저장됨`이다. `저장됨`은 서버 메모리 접수가 아니라 연결된 DB의 쓰기 완료를 뜻한다. 실패 시 `저장 실패 / 다시 저장`을 표시하고 편집을 유지한다.
- 창 닫기·프로젝트 이동 전에 대기 변경을 저장한다. 실패하면 창을 유지하고 `다시 저장` 또는 명시적 `변경 버리기`를 선택하게 한다. 페이지 강제 종료·프로세스 강제 종료 직전 입력은 복구를 보장하지 않는다. unload에서 비밀 포함 Raw를 browser storage에 보관하지 않는다.
- 같은 프로젝트·Evidence의 Request Lab을 다시 열면 요청 이름·순서·현재 REQ·마지막 RES·인증 방식·마지막 선택을 복원한다. 복원된 편집 요청은 계속 편집 가능하다. Original은 관측 기록의 기존 읽기 전용 화면으로 유지한다.
- 새 프로젝트·다른 프로젝트에는 요청을 섞지 않는다. 편집 요청 ×는 해당 작업 항목만 삭제하고 Original·기존 서버 감사 기록은 남긴다. 삭제도 저장되며 늦은 저장이 삭제 항목을 다시 만들지 못하게 한다.

사용자 확인 반영: **× 삭제는 숨김이나 soft delete가 아니라 Request Lab 작업 DB 행의 실제 삭제**다. 이름·현재 REQ·마지막 RES를 함께 제거한다. 삭제 transaction과 revision 갱신이 완료된 뒤 UI 항목/live 참조를 제거한다. 실패하면 항목과 편집 내용을 유지하고 다시 삭제할 수 있게 한다. 삭제 중에는 해당 항목 변경을 잠근다. 늦은 update는 존재하지 않는 ID를 새로 생성하지 못하며 create와 update를 구분한다. 다음 checkpoint·프로젝트 재열기·새 JSON 내보내기에도 삭제 항목이 포함되지 않는다. Original 관측 기록·Evidence·감사 기록 삭제는 이 기능의 범위가 아니다.

## 저장할 값과 비밀값

| 값 | 저장 방식 |
|---|---|
| 안정적인 항목 ID, 이름, 순서, 다음 요청 번호 | 프로젝트·Evidence에 연결해 보관. ID와 표시 이름은 분리한다. 이름은 80 UTF-16 코드 단위 이내이며 서버에서도 마스킹한다. |
| 현재 편집 REQ | 서버에서 마스킹한 HTTP 텍스트. 비밀값을 제외한 요청줄·일반 헤더·본문과 줄바꿈을 보존한다. |
| 마지막 RES | 서버에서 마스킹한 HTTP 텍스트, HTTP 상태, 소요 시간, 바이트 수. 세션 쿠키를 포함한 Set-Cookie도 처리한다. |
| 마지막 결과와 REQ의 연결 | 전송한 편집 revision을 저장하여 이후 REQ 변경 시 `이전 응답`을 복원한다. 과거 REQ 사본을 여러 개 저장하지 않는다. |
| 인증 선택 | ORIGINAL/ANONYMOUS/ACCOUNT 방식만 보관. 세션 토큰·live 헤더값·임시 세션 handle은 저장하지 않는다. |
| 마지막 선택 | 항목 ID 또는 Original. 스크롤·커서·JSON 파생 결과·창 크기는 이번 저장 범위에 추가하지 않는다. |

**현재 AGENTS.md의 비밀값 비저장 원칙을 유지한다.** Authorization·Cookie·비밀번호·API key·토큰 등은 기존 `Masking` 경계를 재사용하며, 헤더뿐 아니라 요청 URL·본문·응답·이름도 확인한다. 프로젝트에 디스크용 마스킹본만 보관하고 실시간 편집 Raw와 분리한다. 화면 저장 실패 메시지나 로그에 Raw를 포함하지 않는다. 마스킹이 안정적으로 끝나지 않으면 해당 저장을 실패로 처리하고 기존 저장본을 유지한다.

재열기 뒤 복원 텍스트는 **비밀값을 제외한 저장본**이므로 바이트 단위 원문 복원이라고 표시하지 않는다. 마스킹으로 제외된 본문 내용은 되살릴 수 없다. `***MASKED***` 등 미해결 값이 남아 있으면 재전송을 잠그고 인증 재선택·필요한 본문 수정 이후에만 허용한다. 현재 세션이 없으면 새 인증을 등록하거나 비로그인을 명시적으로 선택한다. 조용히 다른 계정으로 전송하지 않는다.

현재 프로세스에서 이미 열고 있는 요청의 live 인증값은 저장 직후에도 편집기에 유지한다. 저장 응답의 마스킹 텍스트로 live 편집기를 덮어쓰지 않는다. 마스킹본을 live 상태로 가져오는 것은 실제 복원 시점뿐이다.

## 현재 코드에서 확인한 영향

- `memoryOnlyRawState.ts`: 지금은 닫기·데이터 교체에서 이름·편집 요청·응답을 모두 지운다. 앞으로도 live Raw는 지우되, 서버의 마스킹된 프로젝트 작업 상태는 삭제하지 않는다.
- `FlowScopeExtension.requestLabDraft`: 메모리 원문이 없으면 마스킹된 관측 전문을 `editable=false`로 제공한다. 이 조건을 그대로 사용하면 저장된 편집 요청도 수정·전송할 수 없다. **Original의 편집 불가와 저장 편집 요청의 편집 가능을 별도로 판정**해야 한다.
- `requestLabCredentials`: 현재 세 가지 모드 모두 live Original을 요구한다. 복원된 요청에서 현재 세션·비로그인은 기존 scope/session 검증으로 사용할 수 있게 분리한다. ORIGINAL 복원은 live Original이 있을 때만 허용하며, 마스킹된 저장 인증을 실제 값으로 취급하지 않는다.
- `prepareHumanRequest`: 기존 exact-scope·HUMAN 승인·인증·CRLF/본문 처리 경계를 유지한다. 저장 API가 기존 전송 승인이나 Evidence 생성 경로를 우회하지 않는다. Content-Length·문자 인코딩·마스킹된 본문의 재전송 여부를 추가 점검한다.
- `ProjectStore`·`SqliteProjectStore`·Burp checkpoint: 별도 Request Lab 작업 상태를 프로젝트 로드·저장·JSON 내보내기·자동 checkpoint·종료 flush 모두에 전달해야 한다. 화면의 localStorage만으로 저장을 해결하지 않는다.

## 저장 구조와 성능

프로젝트 `requestLabWorkspace`를 graphWorkspace와 별도로 둔다. 보기·그래프 노드 배치와 연결하지 않고 originEvidenceId로 요청들을 찾는다. 일반 snapshot에는 HTTP 본문을 넣지 않고 Request Lab을 열 때 해당 Evidence의 작업 항목만 조회한다.

조회·변경 API는 기존 loopback capability·origin·host 경계를 사용한다. 변경은 프로젝트/dataset generation, workspace revision, 항목 ID로 검증한다. 저장은 HTTP 전송과 구분하고 요청 ID·변경 revision으로 오래된 완료를 무시한다. 여러 브라우저의 동일 항목 수정 충돌은 마지막 저장으로 조용히 덮어쓰지 않고 충돌 상태와 재조회 선택을 제공한다.

- REQ 편집은 약 800ms debounce, 이름 변경은 확정 시 저장한다. 마지막 RES는 전송 완료 후 한 번 저장한다. 입력 중 전체 프로젝트나 모든 요청을 다시 직렬화하지 않는다.
- 항목별 변경만 마스킹·전송·SQLite upsert한다. 이름만 바꾸면 큰 REQ/RES를 다시 보내지 않는다. 삭제와 revision 갱신은 같은 transaction으로 처리한다.
- SQL 저장과 프로젝트 전체 checkpoint를 동일한 게시/저장 순서에 묶는다. 예전 checkpoint가 더 최신 workspace나 삭제를 덮어쓰지 않게 한다. 단순한 클라이언트 debounce만으로 이 문제를 해결했다고 보지 않는다.
- 현재의 요청 수·편집 크기·응답 보관 한도를 재사용하고, 여러 Evidence의 누적 저장량에도 프로젝트 단위 보관 예산을 둔다. 초기 제안은 마스킹된 작업 텍스트 총 40MiB다. 초과 시 기존 저장본을 유지하며 사용하지 않는 요청 정리를 안내하고, 자동 삭제·본문 자르기는 하지 않는다. 이는 디스크/작업 텍스트 예산이며 전체 JVM·브라우저 heap 한도와는 다르다.
- JSON 내보내기는 명시 실행 시 전체 마스킹본을 포함한다. 일반 이름 수정 때문에 기존 분석을 재실행하거나 큰 snapshot을 배포하지 않는다.

## 호환성과 오류

현재 JSON 스키마는 7, SQLite 구조 버전은 3이다. 새 저장 상태를 잃는 구버전 재저장을 피하려면 신규 저장 형식을 명시적으로 버전 관리한다. 구현 시 JSON 8·SQLite 4로 올리는 안을 기준으로 모든 읽기·쓰기·부분 저장 경로를 점검한다. 버전 상수만 바꾸지 않는다.

새 JAR은 기존 JSON 1~7·SQLite 1~3을 계속 읽고 작업 상태가 없으면 빈 값으로 적용한다. SQLite migration은 기존 기록·Evidence·감사 참조를 유지하는 transaction이어야 한다. 이전 JAR은 새 형식을 조용히 읽고 덮어쓰는 대신 기존 지원 범위 안내로 거부한다. 파일 버전을 수동으로 낮추지 않는다.

저장 대상 DB가 아직 없는 프로젝트는 `프로젝트 저장 필요`로 표시하고 기존 프로젝트 저장 동작으로 연결한다. 사용자가 저장 위치를 정하지 않았는데 임의 파일을 만들거나 `저장됨`이라고 표시하지 않는다. JSON만 내보낸 프로젝트는 이후 변경의 자동 디스크 저장 대상이 아니라는 점을 구분한다.

원 Evidence가 없거나 service가 달라진 항목은 자동으로 다른 Evidence에 붙이지 않는다. 저장본 조회·편집 가능 여부와 실제 전송 가능 여부를 분리하고 전송은 현재 seed·scope·세션 검증을 통과할 때만 허용한다. 7단계의 수집 데이터 삭제·아카이브 동작을 이번 범위에 미리 구현하지 않는다.

## 승인 후 구현 순서와 검증 인계

1. 프로젝트 작업 상태·마스킹·기존 형식 migration과 round-trip 회귀 테스트.
2. revision 검증과 DB transaction을 사용하는 항목별 조회/변경/삭제, checkpoint 충돌 방지.
3. UI 자동 저장·닫기 flush·실패 복구·이름/REQ/RES 복원, 저장 편집본의 편집·인증 재선택 흐름.
4. 기존 HUMAN 전송·그래프·프로젝트 로드 저장 회귀 확인과 README 갱신.

완료 기준: 이름/REQ/최신 RES 수정 → 저장 → 창 닫기 → 프로젝트/JAR 재열기 후 복원. 전송 후 REQ를 바꾸면 기존 RES는 `이전 응답`으로 유지. 삭제 항목은 재열기와 늦은 저장에서 돌아오지 않음. JSON·SQLite 모두 동일. 인증 비밀은 디스크·snapshot·로그·브라우저 저장에서 발견되지 않음. 저장 실패·디스크 부족·DB 잠금·프로젝트 이동·다중 탭 충돌·늦은 응답·shutdown·migration 실패를 확인.

사용자 요청에 따라 제품 Maven/npm/TypeScript/Vitest/Playwright/Burp 검증은 사용자가 실행한다. 지금은 제품 코드를 수정하거나 이 테스트들을 실행하지 않았다. 목업은 합성 페이지 메모리로 동작하며 실제 디스크 저장·실제 인증 적용·실제 전송 검증을 의미하지 않는다. 모바일은 제외한다.
