# Request Lab 저장·삭제 구현 인계

현재 브랜치: `FEAT/request-lab-ui`. 사용자 승인한 저장·삭제 경로를 연결했다. 제품 빌드·자동 테스트·실제 Burp·라이트/다크 런타임 검증은 사용자 요청에 따라 실행하지 않았다. 기존 합성 목업의 확인 결과와 제품 검증을 구분한다.

웹 전용 보관과 비교한 뒤 사용자가 프로젝트 DB 저장을 최종 선택했다. 웹 전용 모드/설정은 추가하지 않는다. 향후 재전송 전용 그래프는 실제 전송 Evidence를 기준으로 설계하며, 이번 변경에는 그래프를 추가하지 않는다.

## 변경 내용

- 프로젝트별·원 Evidence별로 이름, 현재 편집 REQ, 마지막 RES, 인증 방식, 순서/다음 번호, 마지막 선택을 저장한다. 과거 응답 목록을 추가하지 않는다.
- 입력 약 800ms 후 변경 필드만 서버로 보낸다. 이름 확정도 같은 큐로 저장하며 이름 변경 때 SQLite의 REQ/RES 컬럼을 다시 쓰지 않는다. 저장 상태는 DB commit 후 성공으로 표시한다.
- × 삭제는 DB의 `request_lab_requests` 행을 실제 삭제한다. 실패하면 편집 항목을 유지한다. 요청 번호는 재사용하지 않으며 stale revision/update/create를 거부한다. Original·Evidence·감사 기록은 이 삭제의 대상이 아니다.
- 창 닫기/웹 프로젝트 변경 전 pending 저장을 기다린다. 실패하면 창을 유지하며 재시도 또는 명시적 변경 버리기를 제공한다. 페이지 강제 종료 직전 입력까지 보장하지 않는다.
- 서버 마스킹본만 프로젝트에 넣고 live 편집기를 저장 응답으로 덮어쓰지 않는다. 복원한 편집 요청은 계속 편집하며, 계정/원문 인증은 다시 선택해야 한다. 마스킹 표식이 남은 요청은 전송을 차단한다.
- JSON은 토큰 위치를 사용해 비밀 값만 교체한다. 일반 숫자·문자열 표현, 중복 키, 여백/줄바꿈을 유지한다. 파싱 실패·과도한 중첩은 저장본 본문을 가린다. 기존 서버 마스킹을 다른 기능에서 변경하지 않는다.
- 일반 snapshot에 작업 HTTP 본문을 추가하지 않는다. 트래픽 갱신 시 draft 재검증에서도 저장 작업 본문을 제외한다. 자동 checkpoint·수동 DB 저장·JSON 내보내기·이전 프로젝트 복원에 같은 작업 상태를 전달한다.
- JSON 8 / SQLite 4. 이전 JSON 1~7 / SQLite 1~3은 빈 작업 상태로 읽으며 SQLite 부분 저장은 transaction 안에서 필요한 구조를 추가한다. 과거 LLM 평가·Evidence·감사 기록은 그대로 유지한다.

## 추가/보완한 회귀 테스트 (미실행)

- `RequestLabWorkspacePersistenceTest`: JSON/SQLite 왕복, 비밀값 마스킹, JSON 토큰/CRLF 보존, 실제 SQL 행 삭제, 실패 rollback, 삭제 후 update/create 거부, 이름 수정의 HTTP 컬럼 보호, SQLite 1/2/3 migration, 요청 수/크기 한도.
- `FlowScopeWebServerTest`: capability, dataset/revision 충돌, 저장에서 HTTP 전송 없음, 작은 acknowledgement, 저장본 조회, snapshot 제외.
- `requestLabPersistence.test.ts`: debounce, 변경 필드만 저장, 전송 중 편집, 실패 후 순서/재시도, 삭제 실패 시 유지, 저장 후 요청 번호 복원, disposal.
- `RequestLabDialog.test.tsx`: live Original 없이 복원/편집/인증 재선택, 최신 응답 저장, delete commit 대기/실패, 닫기 실패·프로젝트 변경 차단.
- 기존 `ProjectStoreTest`의 새 저장 형식 기대값을 8로 갱신했다.

## 사용자 검증 순서

1. 루트 `mvn clean verify` 실행 후 최신 JAR을 Burp에 올린다.
2. DB가 연결된 프로젝트에서 요청 추가 → 이름/REQ 변경 → 재전송 → `프로젝트 저장됨` → 닫기/재열기 → Burp 종료/재실행을 확인한다. 현재 REQ와 마지막 RES 하나가 복원되어야 한다.
3. 요청 × 삭제 → 닫기/재열기 → 새 트래픽 수집/자동 checkpoint → 재실행에서 돌아오지 않는지 확인한다. 원 Evidence와 감사 기록은 유지되어야 한다.
4. 저장 실패/DB 잠금, 여러 브라우저 수정 충돌, 프로젝트 변경, 비로그인/현재 세션 재선택, JSON/SQLite 내보내기/재열기를 확인한다. 기존 프로젝트는 버전 번호를 직접 바꾸지 말고 새 JAR로 읽는다.
5. 라이트/다크 및 1280/1920px에서 저장 상태/오류/닫기/삭제 조작을 확인한다. 모바일은 제외한다.

보관 한도는 프로젝트 전체 마스킹 작업 텍스트 40MiB와 기존 창 메모리 한도를 각각 적용한다. 인증 비밀은 디스크에 복원되지 않는다. 이전에 따로 내보낸 파일이나 백업까지 ×가 소급 삭제하지는 않는다. 커밋 전 확인은 소스 경로 검토·diff 공백 확인과 graphify AST 갱신으로 제한했다.
