# FlowScope 결정 로그 (Decision Log)

> **운영 원칙 (카파시 마인드).** 최소로 시작한다. 각 선택마다 "더 나은 방식이 있나?"를 묻는다.
> **있으면 교체하고, 없으면 유지하되 기각 이유를 여기 적는다.** 그리고 계속 디벨롭한다.
> 각 항목: **결정 / 왜 / 검토한 대안·기각 이유 / 재검토 트리거 / 상태**.
> 상태: `확정` · `잠정`(더 나은 게 나오면 교체) · `열림`(아직 안 정함).

## D-000 · 결정을 어떻게 기록할까 (메타)
- **결정:** 단일 living 파일에 시간순 append.
- **왜:** 결정 히스토리와 기각 근거가 한곳에 쌓여야 "왜 이렇게 했지?"를 나중에 재구성 가능.
- **대안·기각:**
  - 설계서 §4 인라인 표 — 기각: 대안·기각근거·재검토조건이 안 쌓임.
  - 결정당 파일 1개(ADR 정석) — 기각: 이 규모엔 오버헤드 과함(미니멀리즘 위반).
- **재검토 트리거:** 항목 40개 초과 시 단계별 분할.
- **상태:** 확정 · 2026-08-24

## D-001 · 두 축 분리: source ≠ idn/role
- **결정:** 소스(human/scanner/llm)와 요청자(idn)·권한(role)을 **직교 축**으로 분리.
- **왜:** "누가 발견했나(비교 축)"와 "누구 권한으로 갔나(취약 축)"는 별개. 섞으면 3-way 비교와 IDOR 판정이 동시 오염.
- **대안·기각:** 단일 "행위자" 축으로 통합 — 기각: 사람이 admin으로도 user로도 로그인하는 순간 무너짐.
- **재검토 트리거:** 없음(구조적 결정).
- **상태:** 확정 (프로토타입 이미 이 구조)

## D-002 · 커버리지는 퍼센트 금지
- **결정:** 관측 조합 수 · 갭 개수로만 표기. 비율(%) 안 씀.
- **왜:** 블랙박스 점검이라 전체 조합(분모)을 알 수 없음. 퍼센트는 거짓 정밀도.
- **대안·기각:** OpenAPI 명세로 분모 추정 후 % 표기 — 기각: 명세 없는 대상이 다수, 분모가 틀리면 전부 왜곡.
- **재검토 트리거:** 대상이 완전한 OpenAPI를 제공하는 화이트박스 모드를 지원하게 될 때.
- **상태:** 확정

## D-003 · 미교차는 "관측된 신원·객체 안에서만"
- **결정:** 미교차 후보 = 관측된 (op·resource) × 관측된 idn 중 아직 안 엮인 칸. 전체 가능 공간 아님.
- **왜:** "안 밟은 셀에 취약이 있다"는 증명 불가능한 주장을 피함. 조합 폭발도 방지.
- **대안·기각:** 전체 조합 공간에서 미교차 산출 — 기각: 분모 불가지 + 폭발.
- **재검토 트리거:** 없음(블랙박스 정직성의 핵심).
- **상태:** 확정 (프로토타입 `candidates` 로직과 일치)

## D-004 · 판정 오라클 = 상태 + 소유 + 내용  ★척추
- **결정:** verdict를 상태코드 단독이 아니라 **status taxonomy + owner + 응답 본문(타 소유 객체 포함 여부)**로 판정.
- **왜:** BOLA/IDOR는 "200인데 남의 데이터가 나옴". soft-403(200으로 거부)·빈 200·404-as-deny를 status로 단정하면 취약을 정반대로 판정.
- **대안·기각:** status-only(프로토타입 현재 `verdictOf`) — 기각: 위 오판 케이스. 본문 기반이 필수.
- **재검토 트리거:** 응답 본문을 신뢰 못 하는 대상(암호화/이진)에서 대체 신호 필요 시.
- **상태:** 잠정 → **팀 확정 대기** (설계서 §2.4)

## D-005 · 소유자(owner) = 다중신호 + 사람검수 우선  ★척추
- **결정:** owner를 본문 소유필드·생성(POST) 주체·반복관측 일치로 합산하고, **확정은 사람 검수 우선**.
- **왜:** IDOR 판정 전체가 owner에 의존. 오판 시 하류 전부 노이즈.
- **대안·기각:** "그 자원에 처음 2xx 받은 신원"(프로토타입 현재) — 기각: 남이 먼저 접근하면 소유자 뒤바뀜, 단독으론 저신뢰.
- **재검토 트리거:** 자동 신뢰도가 충분히 높다고 측정되면 검수 부담 완화 검토.
- **상태:** 잠정 → **팀 확정 대기** (설계서 §2.3)

## D-006 · 소유자는 속성, 노드 아님
- **결정:** 그래프에 소유자 노드를 그리지 않고 판정 속성으로만.
- **왜:** 요청자가 이미 맨 앞 열 → 소유자 노드는 중복, 배치 복잡화.
- **대안·기각:** 소유자를 4번째 열 노드로 — 기각: 시각적 중복·교차 증가.
- **재검토 트리거:** 소유관계 자체를 탐색 대상으로 삼는 뷰가 필요해질 때.
- **상태:** 확정

## D-007 · Flow(순서)는 보조 시각화, 판정 무영향
- **결정:** 데이터 의존성(생성 ID·토큰) 기반 순서선. 커버리지·IDOR 판정엔 미반영.
- **왜:** 절차 이해용. 시간순 연결은 무관 요청을 잘못 잇고 커버리지를 왜곡.
- **대안·기각:** 순서를 판정 근거로 사용 — 기각: 인과 아닌 상관을 취약으로 오인.
- **재검토 트리거:** 순서 의존 취약(예: 상태 전이 우회)을 정식 타깃으로 삼을 때.
- **상태:** 확정

## D-008 · 재전송은 액티브·격리·스코프가드
- **결정:** 재전송은 실제 재요청(액티브), 관측 3종과 분리 저장, 스코프 밖 차단 + 사용자 확인.
- **왜:** 관측 데이터 오염 방지 + 안전(상태변경 요청 경고).
- **대안·기각:** 재전송 결과를 관측에 병합 — 기각: 커버리지/판정이 오염됨.
- **재검토 트리거:** 없음(안전·무결성 결정).
- **상태:** 확정

## D-009 · AI는 시나리오 제안에만, 규칙엔진이 본체
- **결정:** 수집·정규화·판정·커버리지/갭은 규칙 기반. LLM은 시나리오 확장(F-17)에만.
- **왜:** 판정 재현성 확보. LLM을 판정에 넣으면 같은 입력에 다른 결과.
- **대안·기각:** LLM이 판정까지 — 기각: 재현성·설명가능성 상실, 논문/신뢰성에 치명.
- **재검토 트리거:** 규칙으로 못 잡는 판정을 LLM 보조로 '후보 제시'만 시키되 사람이 확정하는 형태는 열어둘 수 있음.
- **상태:** 확정

## D-010 · 그래프 = 노드-링크(IDA 스타일) + 매트릭스 병행
- **결정:** 요청자→객체→엔드포인트 3열 + taxi(직각) 엣지. '없는 것(미교차/커버리지)'은 매트릭스로 병행.
- **왜:** 그래프는 '있는 흐름'을, 매트릭스는 '없는 칸'을 잘 보여줌. 둘은 상보적.
- **대안·기각:**
  - force-directed 자동배치 — 기각: 매번 배치가 달라져 추적성 붕괴, 교차 폭발.
  - 매트릭스만 — 기각: 데이터 의존 체인·흐름이 안 보임.
- **재검토 트리거:** 노드 200+ 에서 가독성 붕괴 시 계층 접기/클러스터링 도입.
- **상태:** 확정

## D-011 · 구축 순서 = 레이어링 (Layer 0 그래프 우선)
- **결정:** L0 그래프(수집+정규화+시각화) → L1 IDOR 최소(소유자+타인접근) → L2 풀 비교(미교차·불일치·5-state).
- **왜:** 뼈대(그래프)가 오라클 없이도 즉시 가치. 판정 기계는 위에 얹는 상위 레이어.
- **대안·기각:** 8단계를 한 번에 구현 — 기각: 뼈대 안 서고 판정 미확정 상태에서 상류 작업 리스크.
- **재검토 트리거:** 없음(공정 결정). L0 완료 후 L1 착수 게이트.
- **상태:** 잠정 → **팀 확정 대기**

# 전수 리뷰 반영 (2026-08-24, 6관점 리뷰 + 원본 대조 검증)

> 리뷰 지적 20건 중 코드에서 직접 검증된 것만 결정으로 승격. 지적이라고 무조건 수용하지 않고, 유지할 것은 유지 이유를 적는다.

## D-012 · owner 판정에 응답 본문 소유필드를 1순위로  ← D-005 강화
- **결정:** owner 근거 우선순위를 (1) 응답/요청 본문의 owner·user_id, (2) F-06 신뢰도 점수, (3) **최후에만** first-accessor. 근거 부족/충돌 시 `미확정` → 해당 조합 verdict를 판정에서 제외.
- **왜 (검증된 결함):** 프로토타입 `build()` L58이 `owner = 그 자원에 처음 2xx~3xx 받은 신원`. 관측 순서는 파일 병합 순서(human→scanner→llm concat)라 시간순 보장이 없다. **공격자가 실소유자보다 먼저 파싱되면 IDOR 결론이 정확히 뒤집힌다** (공격자 접근=allow 미탐, 실소유자 정상접근=suspicious 오탐). 샘플 데이터에서 admin이 먼저 관측돼 우연히 맞았을 뿐.
- **대안·기각:** first-accessor 유지 + 경고 표시 — 기각: 판정이 뒤집히는 건 경고로 못 막음. 시간순 정렬로 해결 — 기각: 시간순이어도 공격자가 먼저 접근한 경우 동일하게 뒤집힘(근본 해결 아님).
- **재검토 트리거:** 본문에 소유필드가 없는 API가 다수인 대상을 만나면 (2) 신뢰도 설계 재검토.
- **상태:** 확정 (D-005의 구체화)

## D-013 · 쓰기 계열 2xx는 빈 본문이어도 suspicious 유지
- **결정:** POST/PUT/PATCH/DELETE의 2xx는 본문이 비어도 **부작용 성공 증거**로 보아 비소유자면 suspicious. 빈 본문→undecided 강등은 **GET/HEAD 조회에만** 적용.
- **왜 (검증된 결함):** `verdictOf()` L51이 `body.length>2`가 아니면 무조건 undecided. 성공한 DELETE(204)·대다수 PUT/PATCH는 본문이 비므로, **타인 객체를 실제 삭제·수정한 가장 치명적인 쓰기형 IDOR가 전부 '판단 불가'로 빠진다.** `computeCoverage` L352가 suspicious만 세므로 갭 카운트에도 안 오름.
- **대안·기각:** 빈 본문은 일괄 undecided 유지 — 기각: 가장 심각한 취약을 구조적으로 미탐.
- **재검토 트리거:** 없음.
- **상태:** 확정

## D-014 · BFLA(기능 인가)를 판정 경로에 정식 포함  ← Q3 해소
- **결정:** `verdictOf`에 **role + 엔드포인트 요구레벨**을 인자로 전달. 요구레벨 초과 신원의 2xx = **BFLA suspicious**. role=Admin(요구레벨 충족)의 타 객체 접근은 IDOR suspicious에서 제외/별도 라벨.
- **왜 (검증된 결함):** `verdictOf(evs, owned)`가 role을 받지도 쓰지도 않는다. 결과로 (a) 저권한 User가 관리 기능을 성공 호출해도 그 신원이 admin-scope의 first-accessor면 owned=true→allow로 **완전 미탐**, (b) 관리자의 정당한 사용자객체 조회가 admin≠owner→suspicious로 **오탐**. 명세 F-11 '관리자 접근 별도 분류'·F-10 '요구레벨 추정'이 미구현.
- **대안·기각:** BFLA를 범위 밖으로 두고 IDOR만 — 기각: 명세 F-10이 이미 권한레벨 판정을 요구하고, f17 화면이 BFLA 후보를 표시 중. 명세가 이미 약속한 기능.
- **재검토 트리거:** 없음.
- **상태:** 확정 (열린 질문 Q3 → 해소)

## D-015 · 성공 범위를 2xx로 한정 + soft-403 본문 검사
- **결정:** 성공 판정·owner 배정을 **2xx로 한정**. 3xx는 Location 목적지 검사(로그인/에러면 deny). 200이어도 본문이 에러 스키마(`error`/`forbidden`/`unauthorized`)면 **deny로 강등**.
- **왜 (검증된 결함):** `status>=200&&status<400`이 성공. 302 로그인 리다이렉트(사실상 거부)를 받은 신원이 owner로 등록되어 2차 오탐을 만들고, soft-403(`{"error":"forbidden"}` 200)은 본문 길이>2라 suspicious로 오탐.
- **대안·기각:** 3xx도 성공 유지 — 기각: 리다이렉트는 인가 거부의 대표 패턴.
- **재검토 트리거:** 없음. (D-004 오라클의 구체화)
- **상태:** 확정

## D-016 · OPTIONS/HEAD는 성공·owner 집계에서 제외
- **결정:** 프리플라이트/메타 요청은 owner 배정과 IDOR 판정에서 제외(별도 verdict).
- **왜:** 샘플에도 `OPTIONS /api/orders/202 200`이 있고, 현재 로직상 이게 성공·owner 후보로 집계되어 프리플라이트가 IDOR로 오탐.
- **대안·기각:** 모든 메서드 동일 취급 — 기각: OPTIONS 200은 인가 성공의 증거가 아님.
- **상태:** 확정

## D-017 · 미교차 후보에서 자기소유 제외 + 위험도 정렬
- **결정:** 후보 생성 시 `owner==idn` 제외, (타 소유 && 쓰기 메서드) 위험도 내림차순 정렬 후 상위 N 노출. 헤드라인 카운트는 **cross 후보 수**로.
- **왜 (검증된 결함):** 현재 후보에 자기소유 조합이 섞여 카운트가 부풀고, 위험도 정렬 없이 관측 순서로 80/60개를 잘라 렌더 → **진짜 1순위(타 소유·쓰기)가 상한 밖으로 조용히 누락.** 명세 F-14는 '위험도 상위 우선 표시'를 요구.
- **대안·기각:** 상한만 늘리기 — 기각: 폭발 방지 실패 + 우선순위 문제는 그대로.
- **상태:** 확정

## D-018 · role 자동추정 제거 (명세 F-10 준수)
- **결정:** 토큰 substring `/adm/i` 자동추정 분기를 **제거**. 기본 Unknown + 사용자 수동 지정.
- **왜 (검증된 충돌):** 명세 F-10은 "사용자가 직접 라벨 지정, **자동으로 추정하지 않으며** 확인 불가 시 Unknown"인데 프로토타입 L70은 fp에 'adm'이 있으면 Admin으로 자동 배정. 무작위 토큰이 우연히 'adm'을 포함하면 일반 사용자가 Admin으로 오분류되고, LV1/LV2는 자동 경로가 아예 없음.
- **대안·기각:** 명세를 프로토타입에 맞춰 '휴리스틱 제안 후 사용자 수정'으로 완화 — **기각**: 권한 레벨은 테스트 계정 생성 시 이미 아는 값이라 추정할 이유가 없고, 오분류 비용(BFLA 판정 왜곡)이 편의보다 크다.

## D-019 · Flow(F-09) — 명세를 구현이 따라간다
- **결정:** 데이터 의존성(앞 응답 id/token이 뒤 요청에 등장) 기반 연결로 **구현을 수정**. 시각 파싱 후 시간순 정렬 선행.
- **왜 (검증된 충돌):** 명세/상세표는 "단순 시간순으로 잇지 않고 데이터 의존성(PRODUCES/CONSUMES) 기준"인데, `renderSeq()`는 한 신원의 EVENTS를 **배열 삽입 순서대로 i→i+1로 이을 뿐** 의존성 검사가 전혀 없다. Burp `<time>`도 파싱 안 해서 정렬 기준이 시간도 아닌 **소스 concat 순서(human→scanner→llm)**.

## D-022 · 자원/소유 식별은 규칙 우선, LLM 분류기는 보류(트리거 하에 재검토)
- **결정:** 자원 식별을 규칙으로 처리(부모체인 전체표기 `orders:101/items:5`, 쿼리·본문 id류 추출, GraphQL op명). 규칙으로 못 가르는 모호 케이스는 **미확정→사람검수**. LLM을 자원/소유 분류에 넣는 하이브리드는 **지금 채택 안 함.**
- **기준 평가 (직감 아님):** C1 재현성(D-009 하드요구)·C2 정확성·C3 복잡도(Simplicity)·C4 사람부담으로 비교. 보수는 C1·C3 확실히 우위. 하이브리드의 C2·C4 우위는 **모호 잔여물(미확정 발생률)** 크기에 의존하는데 그 값이 **현재 미측정** → 측정 안 된 이득을 위해 확실한 비용(재현성·복잡도)을 태울 근거 없음.
- **대안·기각:** 하이브리드(LLM 분류 + extractive 제약 + 검증게이트 + op단위 캐시 + 사람승인) — **지금 기각**: 얻는 정확성이 미측정이고 재현성/복잡도 비용은 확실. 단, 할루/slop을 막는 설계(추출은 규칙, LLM은 분류만·생성금지, 값이 원문에 실재해야, "모름" 허용, 교차 일관성 투표, op 1회 라벨+승인)는 재검토 시 그대로 사용.
- **재검토 트리거:** 실트래픽에서 미확정 발생률이 사람이 감당 못 할 수준으로 측정되면 하이브리드 도입.
- **상태:** 잠정 → **팀 확정 대기**

## D-028 · 그래프 UX = 명세 이행 + 조사 보강 (`graph-ux.md`)
- **조사 결과 요지:** 레이아웃(계층+직각)은 현행이 정답. **클러터 방어의 본체는 레이아웃이 아니라 인터랙션**(필터·초점+문맥·접기). 채널 분리 원칙: **source는 엣지, verdict는 노드**(둘을 겹치면 3-way와 판정이 서로 가림).
- **대조 사실:** 조사 권고 상당수를 **명세가 이미 규정**(F-14/F-20 직각·경로부각·접기, F-08 색+형태 색약, F-21 필터, F-22 상세, F-14 위험도 정렬). 즉 재발명이 아니라 **명세 이행**으로 위치시킴.
- **조사가 명세에 더한 것(신규):** 미니맵(mxOutline) · 검색→이웃k홉→확장(DOI) · 노드크기=degree · prefix trie 그룹핑 · **`render()` 전량재생성이 인터랙션을 원천 차단한다는 구현 결함 지적**.
- **기술 판정:** 수백 노드까지 **JGraphX 충분**(D-023 재확인). 임베디드 웹(JCEF+cytoscape)은 Chromium 동봉 비용이 이득 상회 → L2에서 수천 규모 **실측 시** 재평가(2단계 에스컬레이션).
- **내가 놓쳤던 것:** 명세는 그래프와 **매트릭스(F-23)를 동등한 두 뷰**로 두는데 UX 조사를 그래프에만 국한. 갭 판독은 매트릭스가 본체 → 로드맵에 명시적으로 포함해야 함.
- **상태:** 확정(방향), 구현은 순차

## D-029 · [P0 보안] BurpXmlParser XXE — 수정 + 시큐어코딩 규칙 수립
- **결함(재현 확인):** `DocumentBuilderFactory`에 `load-external-dtd`만 끄고 **DOCTYPE·외부 일반/파라미터 엔티티를 허용**. `<!DOCTYPE items [<!ENTITY xxe SYSTEM "file:///etc/hosts">]>` 페이로드로 **실제 `/etc/hosts` 내용이 `RequestRecord.path`로 파싱되는 것을 재현**. 엔티티 확장 DoS(billion laughs)도 가능했음.
- **왜 심각:** 입력 Burp XML은 **점검 대상 트래픽이 담긴 신뢰 불가 파일**(타 팀/외부에서 받을 수 있음). 보안 도구가 입력 파싱에서 로컬 파일을 유출하는 것은 변명 불가.
- **수정:** `newSecureBuilder()` 도입 — `disallow-doctype-decl=true`(1순위, DOCTYPE 자체 거부) + 외부 일반/파라미터 엔티티 false + `ACCESS_EXTERNAL_DTD/SCHEMA=""` + XInclude/EntityReference 확장 off + 차단형 `EntityResolver`. 방어 이중화.
- **검증:** 동일 익스플로잇 재시도 → DOCTYPE 단계에서 차단. 회귀 테스트 4종 추가(`XxeSecurityTest`: 외부엔티티·파라미터엔티티·billion laughs·정상XML 무영향). 총 테스트 19→23 통과.
- **코드베이스 감사:** XML 파서는 이 한 곳뿐(수정 완료). 역직렬화(`readObject`)·명령실행(`ProcessBuilder`/`exec`)·네트워크 송신 싱크 **없음** 확인.
- **규칙(이후 무조건 적용):**
  1. 외부 입력 파싱기(XML/JSON/YAML 등)는 **기본 안전 설정으로 생성**하고, 각 파서마다 회귀 테스트를 둔다.
  2. **신뢰 경계를 명시**: 대상 트래픽·업로드 파일·응답 본문은 전부 비신뢰. (D-020의 응답본문 XSS 금지와 같은 계열)
  3. 새 싱크(파일/네트워크/직렬화/프로세스) 추가 시 **결정로그에 위협 한 줄** 남긴다.
- **상태:** 확정 (수정·검증 완료)

## D-048 · 제품 작업면 = `whs_flow` 기반 localhost Web UI + Burp 최소 제어판
- **변경 이유:** D-045/D-046은 비교 구현의 정보 구조만 Swing으로 다시 만들기로 했지만, 실제 사용 검토에서 Swing 포트가 원본 `whs_flow`의 밀도·탐색성·반응형 배치를 재현하지 못했다. 사용자는 원본 Web UI 자체를 제품 정본으로 선택했다. 이 결정은 D-042~D-046의 Swing/JGraphX UI 구현 선택만 대체하며 수집·분석·신뢰 경계는 유지한다.
- **결정:** Burp 탭에는 exact scope, 포트 분류, Proxy history, project I/O, sample/reset, Web UI 열기와 MCP 연결 복사만 둔다. 그래프·매트릭스·흐름·시나리오·파싱·계정/세션은 번들 `web/index.html` 하나에서 일관되게 제공한다. Cytoscape.js는 로컬 JAR 자원으로만 제공하고 외부 CDN을 사용하지 않는다.
- **런타임:** Burp 축소 JRE에서 `jdk.httpserver` 모듈을 기대하지 않는다(D-040). 기존 `LoopbackHttpServer`를 재사용해 `127.0.0.1`에 bind하고, Host/Origin/세션 capability, CSP, `no-store`, frame 차단, 요청 크기 상한을 적용한다. UI와 API는 Burp unload 때 함께 닫힌다.
- **데이터 계약:** polling snapshot은 그래프 메타데이터만 보낸다. Request/Response 전문은 API 선택 시 마스킹 상태로 지연 로드한다. 객체 식별자가 관측되지 않은 요청은 가짜 scope resource를 만들지 않고 `identity → operation`으로 직접 그린다.
- **검증 경계:** UI는 저장 Evidence를 마스킹된 Burp Repeater 미전송 초안으로만 연다. Montoya가 보장하지 않는 재전송 결과 자동 상관·가짜 응답·상태코드 기반 확정은 제공하지 않는다. 규칙과 LLM은 후보만 만들고 `확정/미확정/폐기`는 Evidence 집합에 묶인 사람 판정이다.
- **배포:** JGraphX 의존성과 고지를 제거하고 Cytoscape.js MIT 고지를 JAR에 동봉한다. 이전 Swing 화면은 삭제 대신 ignored `.local/archive/`에 보존한다.
- **검증:** Web API capability/origin, 서비스 경계 계정·세션, 사람 판정, Repeater 미전송 초안, 경량 snapshot/지연 Evidence/재마스킹을 자동 테스트한다. 브라우저 렌더·Burp Community·crAPI 블라인드 벤치마크는 각각 제품 UI, 실제 확장 런타임, 탐지 성능의 별도 게이트다.
- **상태:** 확정

## D-049 · 베타 최종 판정 = 서버 검증 LLM Evidence 번들
- **변경 이유:** 사용자는 세 소스의 결과를 종합한 마지막 취약점 판정을 LLM이 수행하되, 프롬프트 주장이나 2xx 한 건만으로 확정하지 않기를 요구했다. 기존 D-035/D-041/D-045/D-048의 “사람만 최종 확정”은 자동 검증 목표와 충돌했다.
- **결정:** 일반 `assessment`는 계속 `LIKELY/INCONCLUSIVE/REJECTED`만 허용하는 비최종 의견이다. 별도 `flowscope_submit_validation`만 현재 결정론 finding에 대해 `CONFIRMED/INCONCLUSIVE/REJECTED`를 저장한다.
- **증거 계약:** 원본 Evidence와 검증/대조 Evidence는 존재하며 서로 겹치지 않아야 한다. 검증·대조는 동일한 비기본 `source=LLM, sourceDetail=LLM_VALIDATION, phase=VALIDATION, runId`로 캡처되고 응답이 있어야 한다. 베타의 결정적 판정은 safe GET에 한정하며, 동일 후보 재현 2건 이상과 허가된 정상 대조 1건 이상을 요구한다.
- **오라클:** BOLA는 확인된 외부 소유 객체의 정확한 구조화 응답 성공과 소유자 정상 대조를, BFLA는 명시된 역할 정책과 정상 대조 성공을 요구한다. 반복 성공만 `CONFIRMED`, 반복 명시 거부만 `REJECTED`, 그 외는 `INCONCLUSIVE`다. 문자열 부분일치나 status 단독은 사용하지 않는다.
- **보존:** 프로젝트에서 읽은 validation도 현재 후보와 Evidence로 다시 검증하며, 위조·stale·교차 run 결정은 버린다. 사람의 기록은 계정/역할/소유자 입력과 Evidence-bound 감사·오버라이드로 남는다.
- **대체 범위:** D-035/D-041/D-045/D-048의 최종 판정 주체에 관한 부분만 대체한다. Repeater 미전송, raw credential 비저장, exact scope, ZAP 이중 승인 경계는 유지한다.
- **상태:** 베타 확정

## D-050 · 베타 데이터 신뢰 경계 = 수집 시 차단 + 구조 마스킹 + 서버 UI 정본
- **수집:** SCANNER/LLM의 범위 밖 요청은 응답 후 폐기하는 대신 Proxy request received/sent 단계에서 차단한다. scope와 target의 userinfo/fragment, scope query, 역슬래시·인코딩 traversal은 거부한다. HUMAN/UNKNOWN은 수동 탐색을 깨지 않되 UNKNOWN은 분석·그래프·데이터 흐름에서 격리한다.
- **마스킹:** header 문자열 치환만으로는 JSON/XML/form/multipart 비밀을 보장할 수 없으므로 content type별 구조 마스킹을 저장 전 적용한다. 비밀 키가 보이는 malformed JSON은 fail closed로 본문 전체를 마스킹한다.
- **Evidence:** Evidence ID는 source detail/orchestrator/tool/phase/run, 요청·응답, status/location/timestamp/fingerprint를 포함한 의미 digest로 계산한다. 저장된 ID는 함께 저장한 digest가 재계산값과 같을 때만 보존한다.
- **UI:** coverage cell, gap, missed source, per-source verdict/reason은 Java 분석 결과가 유일한 정본이다. Web JS는 이를 재판정하지 않는다. 전문은 `/api/evidence`에서 최대 200건씩 페이지 조회한다.
- **실행:** 동일 source의 겹치는 run은 거부하고 종료 시 정확한 run ID를 요구한다. ZAP context 활성화 시점은 첫 요청 provenance를 보존하는 D-051이 이 결정을 대체한다.
- **상태:** 베타 확정

## D-051 · P5 실행 자동화 = 명시 범위 교체 + 세 레인 run 경계 + ZAP AJAX 호환
- **문제:** 확장 재로드 뒤 exact scope가 비면 MCP 능동 작업은 안전하게 막히지만, 자동화 클라이언트가 사용자가 승인한 범위를 복구할 방법이 없었다. HUMAN 기준선은 별도 run 경계가 없었고, SPA 경로는 일반 ZAP Spider만으로 충분하지 않았다. ZAP 2.17 AJAX Spider는 일반 Spider의 `inScope/subtreeOnly` 시작 인자와 scan ID 상태 조회를 지원하지 않는다.
- **결정:** 인증된 MCP에 전체 allowlist를 교체하는 `flowscope_set_scope`를 추가한다. 값은 기존 `ScopePolicy`로 먼저 검증하고 빈 범위를 거부하며, SCANNER/LLM run 중에는 바꿀 수 없다. 에이전트는 운영자가 명시한 target만 전달할 수 있고 범위를 추론하거나 확대할 수 없다.
- **세 레인:** Web quick-start가 HUMAN run을 정확한 run ID로 시작·종료한다. ZAP Spider/AJAX/Active는 API 호출 전에 SCANNER lease를 예약하고 실패 시 즉시 해제해 첫 요청부터 provenance를 보존한다. AJAX 완료는 scan ID 없이 `stopped` 상태로 판정하되, 해당 run의 캡처가 0건이면 `NO_SCANNER_TRAFFIC_CAPTURED`를 반환해 브라우저/WebDriver 불일치나 프록시 오류를 성공처럼 표시하지 않는다.
- **소유자:** 중첩된 `owner/user/author/account/customer` principal 객체 안의 명시적 id/email/username/sub/subject만 자동 소유자 신호로 추가한다. 문맥 없는 임의 email/id는 계속 무시하고 요청 본문은 소유권 근거로 쓰지 않는다.
- **기각:** raw 세션을 FlowScope가 저장·배포하는 Session Broker, 임의 host 자동 scope 확대, ZAP 버전별 미지원 인자 전송은 비밀 경계·exact scope·실제 2.17 호환성에 어긋나므로 도입하지 않는다.
- **검증:** MCP scope 정상/오류/active-run 거부, HUMAN 중복·wrong-end, ZAP 시작 실패 lease 정리, scan-ID 없는 AJAX 상태, ZAP 2.17 시작 query, 중첩 principal BOLA를 자동 회귀로 고정하고 실제 Burp/ZAP/crAPI에서 별도 확인한다.
- **상태:** 베타 확정

## D-052 · 계정 실행 세션 = 사용자 명시 캡처 + 프로세스 메모리 전용 broker
- **변경 이유:** secret-free fingerprint binding만으로는 ZAP과 LLM이 같은 테스트 계정으로 실제 요청을 실행할 수 없다. 에이전트 프로세스에 raw 쿠키를 넘기면 노출면과 사용자 개입이 커지고, 인증 회전도 소스별로 달라진다.
- **결정:** 사용자가 Web UI에서 계정을 등록하고 `로그인 캡처`를 명시적으로 시작한 동안 HUMAN 8080 요청의 Cookie/Authorization/CSRF와 응답 Set-Cookie 회전만 `SessionBroker` 프로세스 메모리에 보관한다. account의 exact service, 현재 scope, `ACTIVE` 상태가 모두 맞을 때만 ZAP/LLM 요청에 주입한다. 401·로그인 redirect·invalid-token 응답은 `SUSPECT`, 인증 재료 삭제/만료는 `REAUTH_REQUIRED`로 바꾸고 이후 주입을 거부한다. 403은 역할 거부일 수 있으므로 세션 만료로 보지 않는다.
- **비밀 경계:** raw 값은 RequestRecord, Web/MCP view, 로그, `.flowscope.json`에 넣지 않는다. 교체·폐기·unload에서 broker의 char buffer를 덮어쓴다. 다만 JVM/HTTP API가 짧게 만든 immutable String 사본까지 물리적으로 지운다고 주장하지 않는다. 프로젝트 재개에는 수동 재로그인이 필요하다.
- **D-051 관계:** D-051이 기각한 것은 raw 세션의 지속 저장·배포와 범용 자동 로그인이다. 이 결정은 그 경계를 유지하면서 명시적·메모리 전용 실행 bridge만 도입한다.
- **한계:** CAPTCHA, MFA, WebAuthn, device binding, 서비스별 refresh/login protocol은 일반화하지 않는다. 사람이 다시 로그인하는 재인증 플로우가 제품 경계다.
- **상태:** 베타 확정

## D-053 · LLM 대상 실행 = closed-world 통제 executor + `executionTrust`
- **문제:** 프롬프트가 `curl --proxy 8082`를 지시하면 에이전트가 임의 네트워크 도구·헤더·리다이렉트를 사용하고도 FlowScope가 그 경로를 완전히 통제했다고 증명할 수 없다. 직접 관측을 최종 재현 Evidence로 받아들이면 확정 gate가 프롬프트 준수에 의존한다.
- **결정:** 기본 agent-workspace는 `flowscope_target_request`만 사용한다. 서버가 method·target·scope·body 크기·broker-owned header를 검증하고, Burp HTTP 엔진으로 redirect를 따라가지 않은 한 요청을 전송해 즉시 LLM run Evidence로 저장한다. write method는 `confirmed=true`와 Burp dialog를 모두 요구한다.
- **신뢰 표시:** RequestRecord에 `executionTrust={CONTROLLED,OBSERVED,UNVERIFIED_RUNTIME,IMPORTED,UNKNOWN}`를 추가한다. 결정적 `CONFIRMED/REJECTED` validation은 `CONTROLLED` probe/control만 허용한다. 8082 직접 프록시와 임의 외부 런타임 관측은 비교 source로 남길 수 있지만 `UNVERIFIED_RUNTIME`이라 최종 gate에는 쓸 수 없다.
- **closed-world:** supplied prompt는 web search, Wayback, 외부 API docs, source repository, curl/browser networking을 금지하며 대상 내부 문서는 in-scope 응답으로 관측됐을 때만 사용한다. 이는 제공 에이전트의 동작 계약이지 OS 방화벽이 아니므로 개조된 클라이언트의 외부 통신까지 차단한다고 주장하지 않는다. exact scope와 Evidence trust gate는 서버가 독립적으로 강제한다.
- **상태:** 베타 확정

## D-054 · 독립 비교와 최종 Judge = 서버 가시성 격리 + 세 레인 dataset lock
- **문제:** “Explorer가 먼저 후보를 보지 않는다”는 프롬프트만으로는 HUMAN/SCANNER 결과 누출을 막을 수 없고, Judge 분석 중 새 탐색 트래픽이 섞이면 비교 기준과 finding ID가 변한다. 레코드 존재를 run 완료로 간주하면 중단된 pass도 잠금 조건을 만족한다.
- **결정:** LLM EXPLORATION run이 활성화된 동안 MCP status는 해당 run의 LLM count만 보이고 candidate/cell/gap/finding과 다른 source Evidence를 거부한다. HUMAN/SCANNER/LLM의 정확한 EXPLORATION lease 종료가 모두 기록되고 active run이 없어야 `flowscope_lock_dataset`이 현재 Pipeline.Result를 고정한다. 잠금 뒤 scope·Explorer·scanner 시작을 거부하고 Judge phase만 허용한다.
- **판정 데이터:** 후보·owner·role 오라클은 잠긴 snapshot을 사용한다. 잠금 뒤 생성되는 VALIDATION probe/control은 현재 Evidence 저장소에서 읽어야 하므로 잠긴 records만 조회하지 않는다. 이 실제 순서를 회귀 테스트로 고정한다.
- **프로젝트:** 완료 레인은 별도 선택 metadata로 저장한다. EXPLORATION record가 있다는 이유로 완료를 추론하지 않는다. raw broker session과 active lease, 잠금 객체 자체는 복원하지 않는다. 저장된 최종 validation을 재검증할 때는 COACH_PROBE/VALIDATION을 제외해 pre-Judge 후보 snapshot을 재구성하며, load 후 저장된 완료 metadata로 다시 잠글 수 있다.
- **최종 주체:** Judge가 `CONFIRMED/INCONCLUSIVE/REJECTED`를 작성하지만, 서버의 candidate/evidence/response gate가 authority다. 모델 서술은 gate를 우회하지 못한다.
- **상태:** 베타 확정

## D-055 · 기본 ZAP 레인 = SYSTEM 결정론 workflow, LLM 기능 선택 아님
- **문제:** LLM이 Spider/AJAX/Active 기능을 임의로 고르게 하면 실행 재현성이 낮고 passive queue 미완료, 브라우저 경로 누락, active scan 오사용, “start accepted=scan complete” 오판이 생긴다. 반대로 단일 Spider만 쓰면 SPA와 ZAP native alert 출력이 약하다.
- **결정:** 기본 scanner lane은 `orchestrator=SYSTEM`으로 Traditional Spider → strict-scope Client Spider → Client 실패 시 AJAX Spider fallback → passive `recordsToScan=0` 대기 → native alerts 조회 순서를 고정한다. 시작 전에 SCANNER lease와 optional account를 예약하고, in-scope SCANNER capture가 0이면 완료가 아니라 실패로 기록한다. stage, warning, captured count, alert count를 Web/MCP에서 표시한다.
- **Active Scan:** 기본 기준선에 넣지 않는다. 별도 exact-scope 요청, `confirmed=true`, Burp confirmation을 모두 통과해야 하며 dataset lock 뒤에는 실행할 수 없다.
- **LLM 역할:** Explorer/Judge prompt는 개별 ZAP start tool을 사용하지 않는다. Judge는 잠금 뒤 alert를 advisory input으로 읽되 대응하는 FlowScope Evidence 없이 취약점으로 확정하지 않는다.
- **상태:** 베타 확정

## D-056 · 변경 추적 = 기능 단위 Git commit + 역할별 문서 정본
- **문제:** Changelog만으로는 실제 수정 파일, 변경 이유, 회귀 검증과 미완료 gate를 추적할 수 없다. 반대로 같은 설명을 모든 문서에 복사하면 서로 다른 상태가 남고, 이전 산출물의 검증을 현재 버전에 소급하는 오류가 생긴다.
- **결정:** 모든 코드·동작 변경은 `docs/ko/development-log.md`에 개발/수정 내용, 이유, 영향 파일, 회귀·최종 검증, 남은 한계를 기록한다. 사용자 계약은 `README.md`, 현재 구조는 `architecture.md`, 선택·기각 이유는 `decisions.md`, 릴리스 변화는 `CHANGELOG.md`, 실제 수행 검증은 `beta-validation.md`, 단계 상태는 `product-development-plan.md`를 정본으로 한다. Git 저장소에서는 구현·회귀 테스트·관련 문서를 하나의 기능 단위 commit으로 남긴다.
- **기각:** 모든 변경마다 모든 Markdown을 형식적으로 수정하는 방식은 역사 문서와 현재 계약을 섞고 무의미한 diff를 만든다. 문서만 남기고 Git diff를 생략하는 방식은 정확한 줄 변경과 복구를 보장하지 못한다. 반대로 Git commit만 남기는 방식은 설계 이유와 실험하지 않은 범위를 전달하지 못한다.

## D-057 · 빈 상태 UX와 발표 정본 = 행동 우선 progressive disclosure
- **문제:** beta.3 Web UI는 관측 0건에서도 관측 범위, 역할, 세션 병합, 3-way 갭, 그래프 고급 조작을 모두 보여 준다. 각 기능의 분석 근거는 있지만 처음 쓰는 사용자는 무엇을 먼저 해야 하는지 알기 어렵고, `USER A · USER B · ADMIN` 예시는 ADMIN 계정이 필수라는 오해를 만든다. 설계 근거도 여러 결정과 초기 Swing 조사 문서에 흩어져 발표자가 동일한 논리로 설명하기 어렵다.
- **결정:** 화면별 `사용자 질문 → 설계 이유 → 하지 않는 것 → 발표 문장`은 `ui-product-rationale.md`를 정본으로 한다. 데이터가 없을 때는 `scope → 계정 로그인/HUMAN → 시스템 ZAP → 독립 Explorer/Judge` 행동을 먼저 보여 주고 분석 패널은 관측이 생긴 뒤 단계적으로 노출한다. 두 저권한 계정을 기본 예시로 하고 ADMIN은 BFLA 역할 비교가 필요한 경우의 선택 계정임을 명시한다.
- **기각:** 모든 분석 패널을 항상 펼쳐 “기능이 많아 보이게” 하는 방식은 첫 성공까지의 경로를 숨긴다. 반대로 고급 기능을 별도 설정 화면 깊숙이 제거하는 방식은 실제 분석 중 source·role·gap·Evidence의 동시 비교를 깨므로, 빈 상태에서만 행동 우선으로 축약한다.
- **구현:** 관측 0건이면 좌측 필터·분석 stage·상세·하단 상태를 숨기고 네 단계와 `빠른 시작 열기`·`샘플로 화면 익히기`만 노출한다. ADMIN은 선택 사항이고 BOLA에는 서로 다른 최소 권한 계정 두 개를 권장한다는 경계를 같은 화면에 적는다. Evidence가 생기거나 샘플을 불러오면 기존 분석 작업면으로 전환하며 계정 화면 진입은 빈 상태에서도 허용한다.
- **검증:** Web 응답 계약 테스트와 `mvn clean verify` 131 tests를 통과했다. 1280×720 standalone의 실제 0-Evidence 화면에서 분석 패널 비노출, quick-start 모달, 샘플 뒤 분석 화면 전환, overflow 0, 콘솔 오류 0을 확인했다. Burp 내 Web UI 실검증은 수동 gate다.
- **상태:** 구현·자동 회귀·standalone 검증 완료, Burp 수동 검증 대기

## D-058 · 공개 설치 산출물 = 사용자가 선택할 수 있는 Burp JAR 하나
- **문제:** Maven Shade가 배포 fat JAR과 함께 `target/original-flowscope-1.2.0-beta.3.jar`를 만든다. 사용자가 중간 JAR을 선택했을 때 Burp는 빠진 runtime dependency의 실제 원인 대신 `Extension class is not a recognized type`이라는 일반 오류를 표시했다. README가 올바른 이름을 적어도 같은 폴더의 유사 파일은 정상적인 사용자 혼동을 만든다.
- **결정:** 공개 install surface에는 Burp에 로드 가능한 fat JAR 하나만 둔다. thin/intermediate JAR이 빌드에 필요하면 사용자가 선택하는 배포 경로 밖의 내부 디렉터리로 이동하거나 package 종료 시 제거한다. 자동 배포 검증은 파일명·단일성뿐 아니라 실제 Burp Community 신규 load를 별도 수동 gate로 요구한다.
- **기각:** README 경고만 추가하는 방식은 현재 beta의 즉시 완화로는 사용하지만 최종 해결이 아니다. 사용자가 파일명을 정확히 구분해야 하는 구조를 제품 계약으로 유지하지 않는다.
- **구현:** Jar 플러그인은 Shade 후처리 입력을 매 package마다 다시 만들도록 `forceCreation=true`로 고정한다. Shade가 주 fat JAR으로 교체한 뒤 package 마지막에 정확한 `original-${project.build.finalName}.jar`만 삭제하고, `target/*.jar` 수가 1이 아니면 빌드를 실패시킨다.
- **검증:** `mvn clean verify` 131 tests 통과 뒤 `clean` 없이 `mvn -DskipTests package`를 다시 실행했다. 두 번 모두 공개 JAR은 한 개였고 크기·SHA-256이 동일했으며 ZIP/manifest 검증을 통과했다. 올바른 이전 JAR의 Burp 2026.7.3 load는 사용자 환경에서 통과했지만 현재 재생성 JAR load는 수동 gate다.
- **상태:** 패키징 구현·자동 검증 완료, 현재 JAR Burp 재로드 대기

## D-059 · 트래픽 노이즈 = 삭제 규칙이 아닌 Evidence 보존형 분류
- **문제:** 경로 확장자, `OPTIONS`, cookie 존재, telemetry라는 이름만으로 관측을 버리면 API처럼 보이지 않는 보안 관련 요청을 영구 미탐으로 만들고 과거 관측에 규칙을 소급할 수 없다. 반대로 모든 브라우저 보조 요청을 그래프에 넣으면 세션 cookie 회전과 정적·navigation 반복이 identity/operation을 폭증시킨다.
- **결정:** 저장과 분석 입력을 분리한다. 모든 관측은 마스킹 후 Evidence로 남기고, 결정론 `TrafficClassifier`가 class, `INCLUDE/EXCLUDE/REVIEW`, 근거, override 여부를 파생한다. coverage/graph에는 `EXCLUDE`만 빼며 `REVIEW`는 포함한다. operation별 `INCLUDE/EXCLUDE/AUTO`를 프로젝트에 저장하고 언제든 되돌릴 수 있지만 no-response, unknown source, non-discovery phase는 override할 수 없다. 반복 접기는 화면 표현에만 적용하며 모든 Evidence ID와 시간·횟수를 보존한다.
- **고신뢰 제외:** 진짜 CORS preflight는 `OPTIONS + Access-Control-Request-Method`, 정적 자원은 안전 메서드와 Fetch destination/MIME 또는 확장자/MIME의 합치, navigation은 document/iframe과 HTML 응답의 합치가 있어야 한다. 객체 신호, 401/403, login redirect, unsafe method, API media type은 제외보다 우선한다. no-response와 `VALIDATION/COACH_PROBE`는 discovery coverage에서만 제외한다. telemetry 이름은 단독 근거가 아니므로 `REVIEW`다.
- **신원 안정화:** cookie 존재는 인증 증명이 아니다. 원 cookie/session 단방향 fingerprint는 account binding 후보로 보존하되, broker exact credential match나 명시 binding이 없는 것은 서비스별 `UNRESOLVED` graph identity 하나로 표시한다. 명시 HUMAN anonymous pass도 Authorization과 Cookie가 모두 없을 때만 `ANONYMOUS`다. 이 방식은 회전 cookie 1,000개를 1,000명의 사용자로 오인하지 않으면서 서로 다른 미확인 계정을 확정 병합하지 않는다.
- **근거:** [W3C Fetch Metadata](https://www.w3.org/TR/fetch-metadata/)는 요청 문맥 신호의 의미를, [WHATWG Fetch](https://fetch.spec.whatwg.org/)는 CORS preflight 헤더를, [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)는 method safety와 representation metadata를 정의한다. [W3C Beacon](https://www.w3.org/TR/beacon/)처럼 background/telemetry 요청도 application data를 보낼 수 있으므로 명칭 기반 삭제는 정당화되지 않는다. Burp와 mitmproxy의 filter도 원 history/flow를 삭제하지 않는 표시 계층이라는 점을 참고했다.
- **기각:** 확장자 blacklist, `/analytics` 정규식, 모든 OPTIONS 제거, cookie 값마다 graph identity 생성, LLM이 매 요청을 분류하는 방식은 각각 미탐·identity 폭증·비결정성·비용 문제 때문에 채택하지 않았다. 학습형 classifier도 ground-truth dataset과 설명 가능한 안정 gate가 없어 현재 제품 경계 밖이다.
- **한계:** Fetch Metadata와 MIME은 누락·오표기될 수 있고 business API와 navigation/asset의 형태가 겹칠 수 있다. 따라서 오탐·미탐 0을 보장하지 않으며, 애매한 관측은 `REVIEW`로 남기는 것이 의도된 결과다.
- **후속 변경:** `REVIEW`를 coverage/graph에 포함한 부분만 D-064가 대체한다. Evidence 보존, 고신뢰 제외 기준, operation override, 신원 안정화 원칙은 유지한다.
- **상태:** 베타 구현·자동 회귀·standalone UI 검증 완료. 실제 다양한 대상의 분류 품질은 blind benchmark와 운영 표본으로 측정해야 함.

## D-060 · HUMAN 브라우징과 Evidence 범위 = 이동 허용, 저장은 exact scope
- **문제:** SCANNER/LLM만 active send gate를 거치고 HUMAN response capture에는 scope 검사가 없어서, 진단 scope 입력이 실패하거나 비어 있을 때 사용자가 잠깐 방문한 네이버 같은 외부 사이트가 FlowScope 신원·그래프에 섞였다.
- **결정:** HUMAN의 일반 브라우저 이동은 Burp에서 차단하지 않는다. 대신 공통 `capture()` 진입에서 source와 무관하게 현재 exact scope를 다시 검사하고 범위 밖 응답은 RequestRecord로 만들기 전에 무시한다. 비프록시 Burp tool capture도 같은 경로를 사용한다. Proxy history/XML import는 기존 scope retention을 유지한다.
- **기각:** HUMAN 범위 밖 요청을 프록시에서 drop하면 진단 중 문서·로그인 보조 이동까지 브라우저가 망가진다. 범위 밖 데이터를 저장한 뒤 UI에서만 숨기면 신원·후보·프로젝트와 Judge 입력이 이미 오염될 수 있다. scope 적용 시 기존 Evidence를 자동 삭제하면 사용자의 수집물이 예고 없이 사라지므로 수행하지 않는다.
- **운영:** 수정 전 또는 scope 적용 실패 중 이미 들어온 범위 밖 Evidence는 사용자가 `수집 초기화`로 한 번 지운다. 이후 `http://127.0.0.1:8888/`처럼 유효한 scope를 먼저 적용한다.
- **상태:** 구현·회귀 완료, 현재 JAR의 Burp 실수집 재확인 필요.

## D-061 · source 시각 문법 = 파랑/빨강/검정 + 선형 + H/S/L
- **문제:** source palette가 HUMAN 파랑, SCANNER 청록, LLM 보라였고 SCANNER/LLM 색 변수가 일반 버튼·포커스·선택 상태에도 재사용됐다. 색만 바꾸면 스캐너와 무관한 UI까지 빨개지며, 기존 `B/Z/L` 약어는 일반 HUMAN/SCANNER source 축을 Browser/ZAP으로 축소해 `OTHER_SCANNER`와 맞지 않았다.
- **결정:** source view를 HUMAN=`#2563EB` 파랑·실선·H, SCANNER=`#DC2626` 빨강·파선·S, LLM=`#111827` 검정·점선·L로 고정한다. 동일 관계의 source edge는 기존의 서로 다른 taxi turn으로 평행 분리하고, 색을 보지 못해도 선형과 H/S/L로 식별할 수 있게 한다. 일반 조작은 별도 `--accent`를 사용하고 authorization verdict palette는 별도 축으로 유지한다.
- **기각:** 세 source를 색만 다른 겹친 실선으로 그리면 위쪽 edge가 아래 edge를 가리고 색각·흑백 환경에서 출처가 사라진다. 반대로 source마다 완전히 별도 그래프만 제공하면 3-way 중복·누락을 한 좌표에서 비교하는 제품 목적이 약해지므로 필터와 평행 overlay를 유지한다.
- **검증:** Web 응답 계약에서 세 CSS token과 H/S/L 약어를 고정하고, 정적 검색으로 source 변수가 일반 UI accent에 남지 않는지 확인한 뒤 전체 Maven 검증과 브라우저 렌더를 수행한다.
- **상태:** 구현·자동 회귀·1280×720 standalone 렌더 검증 완료. 실제 Burp Web UI 재로드 확인은 수동 gate.

## D-062 · 공개 문서 언어 경계 = 루트 한국어 + 언어별 디렉터리
- **문제:** 한국어 사용자를 대상으로 진행하는 프로젝트인데 저장소 첫 화면과 공개 운영 문서가 영어이고, 상세 한국어 문서와 영어 문서가 같은 경로에 섞이면 어떤 문서가 정본인지 불명확해진다.

- **기각:** 모든 문서를 자동 번역해 양쪽 디렉터리를 대칭으로 채우면 검토되지 않은 표현과 기술적 의미 차이를 정본처럼 유통하게 된다. 언어 표시 없이 한 디렉터리에 혼합하면 사용자가 문서 언어와 최신성을 예측할 수 없다.

## D-063 · HUMAN 비교 구간 = 명시적 exploration pass만
- **문제:** exact scope는 네이버 같은 다른 대상의 혼입은 막지만, 같은 scope의 로그인 준비·배경 이동·HUMAN pass 밖 요청까지 `BASELINE` coverage에 넣어 HUMAN 발견량과 3-way gap을 부풀렸다. Session Broker 로그인 캡처도 세션 준비인지 탐색인지 데이터에서 구분되지 않았다.
- **결정:** HUMAN 로그인 캡처는 `SESSION_SETUP`, Web quick-start가 시작한 HUMAN pass는 `EXPLORATION`, 그 밖의 HUMAN 관측은 `BASELINE`으로 기록한다. 세 phase 모두 마스킹된 Evidence로 보존하지만 HUMAN 3-way coverage·gap·graph에는 `EXPLORATION`만 넣는다. 샘플 HUMAN 레코드도 실제 탐색을 표현하도록 `EXPLORATION`으로 정정한다.
- **기각:** 로그인 요청을 모두 폐기하는 방식은 endpoint inventory·감사 Evidence를 잃어 기각했다. 로그인 path 정규식으로 분리하는 방식은 사이트별 path와 API를 오분류해 기각했다. scope 내 HUMAN 요청을 모두 탐색으로 계속 계산하는 방식은 사용자가 통제하지 않은 시간대를 HUMAN 성과로 위장해 기각했다.
- **검증:** 먼저 HUMAN `BASELINE` JSON API가 coverage에 들어가는 실패 회귀를 재현한 뒤, `SESSION_SETUP`/`BASELINE` 제외·`EXPLORATION` 포함과 capture phase 매핑을 테스트로 고정했다. 실제 Burp 로그인 캡처와 HUMAN pass 전체는 수동 beta gate에 남긴다.
- **상태:** 구현·자동 회귀 완료, Burp 수동 확인 대기

## D-064 · REVIEW = 메인 비교가 아닌 명시적 검토 대기
- **문제:** D-059는 애매한 요청을 잃지 않기 위해 `REVIEW`도 coverage/graph에 넣었다. 그 결과 반복 polling처럼 분류기가 이미 애매하다고 표시한 관측까지 확정 `INCLUDE`와 같은 3-way cell·gap을 만들었고, UI의 `분석` 수와 `검토` 수가 겹쳐 사용자가 메인 비교의 경계를 알기 어려웠다.
- **결정:** `INCLUDE`만 coverage·graph·인가 분석·3-way gap 입력으로 사용한다. `REVIEW`는 전체 Evidence, 파싱 결과, 상세 Request/Response, MCP Evidence 목록에 그대로 남기고 별도 검토 대기 수로 센다. `EXCLUDE`도 Evidence로 보존하되 기본 표시에서 숨긴다. UI 처분 필터 기본값은 `INCLUDE+REVIEW`이며 사용자는 operation 단위 `INCLUDE/EXCLUDE/AUTO`로 재분류할 수 있다. Judge는 잠긴 Evidence의 `REVIEW`도 별도로 triage하지만 gap이나 REVIEW 자체를 취약점 증거로 승격하지 않는다.
- **기각:** `REVIEW` 삭제는 미탐을 복구할 수 없어 기각했다. `REVIEW`를 계속 메인 graph에 넣는 방식은 노이즈 감소와 상호 배타 통계를 달성하지 못해 기각했다. 정적 점수 임계값으로 자동 승격하는 방식은 검증된 ground truth와 calibration이 없어 벤치마크 전에는 넣지 않는다.
- **한계:** MIME·Fetch Metadata가 빠진 실제 API가 `REVIEW`에 남아 메인 비교에서 보류될 수 있다. 따라서 사용자는 lock 전 검토 대기를 확인해야 하고, blind benchmark에서는 REVIEW 작업량과 승격률을 별도 측정한다. 오탐·미탐 0을 주장하지 않는다.
- **검증:** 반복 polling 3건이 기존 코드에서 모두 coverage에 들어가는 실패를 먼저 재현했다. 이후 Evidence 3·REVIEW 3·coverage 0·EXCLUDE 0 경계와 Web snapshot의 세 처분 수를 회귀로 고정한다.
- **상태:** 구현·자동 회귀·1280×720 standalone 상호작용 확인 완료, 실제 Burp UI와 blind benchmark 확인 대기

## D-065 · 인가 oracle 오염 방지 = 성공 응답 owner + 대상 객체 ID
- **문제:** D-015·D-016은 owner 배정을 성공한 2xx 비메타데이터 응답으로 제한했지만 구현은 401/403과 HEAD 본문의 owner 필드도 확정 근거로 모았다. 또한 로그인 redirect 정규식 `/auth`가 `/authority`를 거부로 오인했고, 객체 포함 검사가 대상 ID와 owner 중 하나만 보여도 참이라서 owner 문자열만으로 BOLA 후보와 최종 `CONFIRMED` gate를 통과할 수 있었다.
- **결정:** 자동 owner 후보는 `ResponseEvidence.successful`인 OPTIONS/HEAD 이외 응답에서만 수집한다. 로그인 redirect는 `login/signin/auth/authorize/error/forbidden/unauthorized`의 완전한 경로 세그먼트만 인정한다. BOLA 읽기 Evidence는 응답의 구조화된 `id`가 대상 resource의 최종 ID와 일치해야 하며 owner 문자열만으로는 객체 포함을 인정하지 않는다. 소유권 identity 매핑과 객체 포함 검사는 서로 다른 oracle로 유지한다.
- **기각:** owner 문자열만으로 대상 객체를 인정하면 unrelated metadata가 최종 확정까지 오염된다. 반대로 응답 owner 문자열을 내부 `user-a`와 직접 비교하면 이메일·JWT subject·계정 ID처럼 표현이 다른 정상 증거를 미탐하므로 객체 ID 판독기에 섞지 않는다.
- **한계:** 응답이 대상 객체 ID를 반환하지 않는 API는 자동 BOLA 읽기 확정이 `UNDECIDED/INCONCLUSIVE`에 남을 수 있다. 이는 후보를 삭제하거나 안전하다고 판정하는 것이 아니며, 향후 검증된 target-specific oracle 없이는 자동 승격하지 않는다.
- **검증:** 기존 코드에서 거부/HEAD owner 오염 1건, `/authority` redirect 오탐 1건, owner-only 객체 오탐 1건을 실패 테스트로 재현했다. 수정 후 인가·객체 Evidence·MCP 최종 gate 집중 30 tests와 전체 `mvn clean verify` 137 tests가 통과했다.
- **상태:** 구현·자동 회귀 완료, 실제 Burp/Judge 전체 workflow 확인 대기

## D-066 · 스캐너 신원 격리 = fresh ZAP session + broker credential replacement
- **문제:** 한 ZAP 상태에서 비로그인과 여러 계정을 순차 실행하면 cookie jar·crawler state·Alert의 신원 provenance가 섞인다. 계정 전환 때 새 broker 헤더만 덧붙이면 ZAP이 이미 가진 Authorization/Cookie와 충돌할 수 있고, 자격증명 material만 본 캡처를 ACTIVE로 사용하면 로그인 실패 세션을 다른 실행기에 배포할 수 있다. 반대로 비로그인 레인의 Cookie를 매 요청 제거하면 그 레인에서 새로 생긴 익명 세션·CSRF까지 끊어 탐색 성능이 낮아진다.
- **결정:** 사용자는 Web/MCP에서 비로그인과 ACTIVE 계정을 복수 선택한다. SYSTEM scanner campaign은 비로그인 뒤 선택 계정을 순차 실행하며 각 신원 앞에서 ZAP `core/newSession`을 성공시켜야 한다. 계정 레인은 broker 소유 헤더를 전부 제거한 뒤 해당 ACTIVE 계정 값만 주입한다. 비로그인 레인은 Authorization/Proxy-Authorization을 제거하되 fresh session 안에서 새로 발급된 Cookie/CSRF는 유지한다. 신원별 zero-capture 또는 단계 실패가 하나라도 있으면 SCANNER 완료 gate를 열지 않는다. Alert와 상태에는 account/run provenance를 붙인다.
- **세션 확인:** 같은 service의 동시 로그인 캡처는 한 계정만 허용한다. material 뒤 401·로그인 redirect·invalid-token이 아닌 2xx~4xx 응답이 관측되어야 `ACTIVE`이며, 없으면 `UNVERIFIED`다. 403은 역할 거부일 수 있어 일반 세션 만료 신호로 쓰지 않는다.
- **기각:** 계정마다 사용자가 ZAP context·script를 수동 구성하는 방식은 제품 자동화와 비교 재현성을 훼손한다. 한 session에서 헤더만 교체하는 방식은 cookie/crawler state를 격리하지 못한다. 비로그인 매 요청의 모든 Cookie 제거는 상태형 공개 흐름을 파괴한다. 모든 localhost 차단은 허가된 로컬 benchmark를 막으므로 Web 제어면의 실제 port만 target에서 제외한다.
- **한계:** `ACTIVE`는 범용 transport 확인이지 서비스 고유 `/me`, 계정 소유, role 증명이 아니다. ZAP 전역 replacer/script처럼 fresh session 밖에서 강제되는 사용자 설정은 자동 제거하지 않는다. ZAP 2.17 실제 cookie jar·browser와 Burp listener를 연결한 전체 실행은 아직 수동 gate다.
- **검증:** 기존 API가 없어서 컴파일 실패하는 회귀를 먼저 만들고, successful response 전 `UNVERIFIED`, 같은-service 동시 캡처 거부, 관리 헤더 목록, run 중 account 전환, ZAP newSession, 비로그인→USER A→USER B 순서·3회 reset·lane 상태, Web 복수 선택 contract, LLM context account 전달, Web 자기 제어면 거부를 자동 테스트로 고정했다. 전체 `mvn clean verify` 144 tests가 통과했다.
- **상태:** 구현·자동 회귀 완료, 실제 Burp/ZAP/로그인 전체 캠페인 확인 대기

## D-067 · 응답 provenance = 요청 시점 문맥 고정 + 선택 계정 exact match
- **문제:** Proxy 응답을 받을 때의 전역 run context를 사용하면 ZAP이 다음 계정 lane으로 전환하거나 HUMAN pass가 끝난 뒤 도착한 늦은 응답이 다른 run·계정으로 기록될 수 있다. 또한 HUMAN pass dropdown의 선택값을 그대로 신원으로 믿으면 USER A를 선택한 상태에서 USER B 또는 비로그인 브라우저를 사용해도 USER A Evidence로 오염된다. fresh anonymous ZAP lane에서 서버가 발급한 쿠키를 일반 미연결 쿠키처럼 해석하면 하나의 비로그인 lane이 `UNRESOLVED` 신원으로 바뀐다.

SYSTEM 소유 fresh anonymous ZAP lane은 lane-local Cookie/CSRF가 생겨도 `ANONYMOUS`로 유지한다.
- **상한·비밀 경계:** in-flight 문맥은 20,000건과 10분 TTL로 제한하고 unload 시 폐기한다. 이 표에는 raw Cookie·Authorization을 복사하지 않는다. 응답 상관 항목이 없으면 기존 현재 문맥 fallback을 사용하되 결정적 SYSTEM 실행은 정상 request/response 쌍을 회귀·실환경에서 확인한다.

- **검증:** HUMAN 선택 계정의 exact match/mismatch, 로그인 캡처 우선, SYSTEM anonymous Cookie의 `anon` 유지, request-time scanner context를 자동 회귀로 고정했다. Burp Community 2026.7.3에서 현재 JAR을 로드하고 HUMAN listener 8080을 통한 `curl` 3건, ZAP 2.17 SYSTEM 기준선 8건, MCP 통제 Explorer 요청 1건을 실제 수집했다. `BROWSER` detail은 listener profile에서 붙었으므로 실제 Burp Browser 검증으로 소급하지 않는다. ZAP 8건은 모두 `CONTROLLED/ANONYMOUS`였고 MCP 범위 밖 요청은 차단됐다. 세 lane 12건의 dataset lock, 후보·gap 0건, 잠금 뒤 Explorer 재시작 거부도 확인했다. 사후 재검토에서 세 source의 유일한 `INCLUDE`였던 `/manifest.json`은 classifier v2의 `+json` 오분류로 확인됐으므로 이 잠금은 wiring 검증일 뿐 business API 탐색 품질 검증이 아니다. 실제 USER A/B 로그인과 늦은 응답 lane 전환은 계속 별도 수동 gate다.
- **상태:** 구현·자동 회귀·anonymous wiring 검증 완료, 실제 Burp Browser와 복수 로그인 계정 실환경 gate 대기

## D-068 · HUMAN 공격면 = 관측 graph와 provenance-backed route candidate를 분리
- **문제:** 현재 graph와 `UNCROSSED`는 실제 `INCLUDE` request/response만 사용한다. 이 경계는 정직하지만 응답에서 참조된 아직 미요청 endpoint를 보여 주지 못한다. 반대로 후보를 관측 edge처럼 합치면 사람이 실제로 밟지 않은 경로가 HUMAN coverage와 finding을 오염시킨다.
- **결정:** 기존 `UNCROSSED`는 관측 identity × 관측 operation/resource의 미실행 cell로 유지한다. 별도 `RouteCandidate`는 exact-scope Burp Site Map 미응답 항목과 저장된 HTML/form, redirect, sitemap/robots, manifest, 보수적 JS URL literal, 대상에서 관측한 OpenAPI에서만 만들며 provenance ID를 필수로 한다. candidate는 중립 시각 문법으로 표시하고 실제 request-response가 생기기 전에는 coverage, owner, verdict, finding, lane 완료에 사용하지 않는다.
- **노이즈:** web manifest와 navigation/static metadata는 business graph에서 제외하되 route discovery 입력으로 재사용한다. `REVIEW`는 요청은 있었으나 API 여부가 애매한 상태이고 route candidate는 요청 자체가 없다는 점을 UI와 수량에서 분리한다.
- **가중치:** 근거 없는 confidence 퍼센트는 넣지 않는다. beta.3이 모든 object candidate에 고정 `1.0`을 내려 UI가 `신뢰도 100%`로 표시하던 값은 추출 근거 enum으로 교체한다. beta.4 route candidate는 적용 가능성·명시 method·object template·state-changing·복수 provenance의 범주형 사전식 정렬과 이유를 노출한다. 미요청 후보에 연결되지 않은 authorization 신호는 있는 것처럼 쓰지 않는다. 수치 가중치는 고정 corpus와 blind benchmark에서 feature별 성능·검토 비용을 측정한 뒤 별도 결정한다.
- **근거:** W3C Fetch Metadata와 Web App Manifest, PortSwigger Site Map의 requested/unrequested 구분, Montoya SiteMap API, OWASP IDOR/BOLA testing guidance. 세부 링크와 gate는 `product-development-plan.md` P4-H가 정본이다.
- **구현:** classifier v3가 manifest/source map/service worker를 `DISCOVERY_METADATA`로 분리하고 같은 service·operation의 강한 API Evidence만 immutable discovery gate 안에서 교차 보강한다. RouteCandidate는 project에 왕복되고 Web의 별도 수량·필터·중립 노드·상세에서 provenance와 범주형 정렬 이유를 노출한다. object의 고정 100% confidence는 path/query/body/GraphQL/derived 근거 enum으로 교체했다.
- **검증·한계:** beta.4 당시 자동 회귀와 standalone 1280×720·600×800 화면 검증을 완료했다. 당시 후보 추출은 저장된 8KiB 응답 안의 정적 literal에 제한됐고, beta.8의 D-073에서 보존 전문 우선·metadata-only 시 preview fallback으로 확장됐다. 동적 JavaScript·런타임 생성 경로는 여전히 추측하지 않는다. 실제 Burp Community에서 새 JAR의 응답 없는 Site Map item, 실제 Burp Browser HUMAN pass, candidate가 있는 그래프를 확인하는 수동 gate와 공개 confusion matrix는 남아 있다.
- **상태:** beta.4 구현·자동 회귀 완료, Burp 실환경 gate 대기

## D-069 · route discovery = 공통 코어 + 무상태 포맷 어댑터

- **문제:** HTML 정규식, JSON 전용 OpenAPI, 제품별 XML 규칙을 추출기 하나에 계속 추가하면 scope·method·정규화·dedup 규칙이 포맷마다 달라진다. 특히 같은 path의 관측 `GET` 때문에 method 근거 없는 `UNKNOWN`까지 관측으로 간주하면 실제로 시도하지 않은 조합이 coverage처럼 보인다.
- **결정:** 모든 입력을 `RouteDiscoveryDocument`로 만들고 HTML, 정적 JavaScript, OpenAPI/Swagger JSON·YAML, 표준 metadata, generic XML 어댑터는 원시 참조와 method 근거만 반환한다. exact scope, http(s) scheme, method token, URI/path 정규화, `service + method + path` dedup, provenance 병합, observed 승격은 `RouteCandidateExtractor` 공통 코어만 수행한다.
- **provenance 계약:** type과 Evidence ID를 분리된 set으로 저장하지 않고 `(type, evidenceId, source, runId, adapter)` 튜플로 보존한다. 프로젝트 schema v1은 새 배열을 읽고 쓰며, 구버전의 분리된 배열은 대응을 꾸며내지 않고 `LEGACY_UNMAPPED/UNKNOWN/legacy-project` provenance로 보수적으로 이관한다.
- **포맷 경계:** HTML은 네트워크를 사용하지 않는 HTML5 DOM 파싱, JavaScript는 정적 literal call site만, OpenAPI는 관측된 JSON/YAML만, XML은 제품명 없는 명시 URL/method 문법만 처리한다. XML DOCTYPE·외부 entity·외부 DTD/schema는 차단한다. 동적 JavaScript 실행·전체 AST·framework 전용 의미 해석은 후속 어댑터이며 공통 코어를 바꾸지 않는다.
- **검증 경계:** 일반 protocol fixture 7종의 truth route 18개에서 TP 18/FP 0/FN 0을 회귀로 고정하고 negative CSS·범위 밖·동적 문자열·XXE·`UNKNOWN` 오승격을 검사한다. 이 corpus는 구현과 함께 만든 기능 회귀 자료이지 blind benchmark나 실제 공격면 성능 주장이 아니다.
- **의존성:** jsoup은 로컬 HTML 파싱에만 사용하고, Jackson YAML/SnakeYAML은 관측 OpenAPI YAML 파싱에만 사용한다. Shade는 Jackson service metadata를 병합하며 번들 라이선스·NOTICE를 포함한다.
- **상태:** 공통 코어 구현 및 자동/fat-JAR smoke 검증 완료. 실제 Burp Site Map·Burp Browser와 blind target gate는 열림.

## D-070 · 독립 Explorer route 시야와 dataset lock = provenance 단위 재계산

- **문제:** D-054는 Explorer의 record/cell/gap/finding 시야를 격리했지만, lock 전 active LLM run이 없을 때 `flowscope_get_status`가 전체 source count와 active run을 반환했다. route candidate는 MCP 도구가 없었고, 전역 후보의 top-level observed/applicability를 그대로 필터하면 HUMAN 근거가 LLM 시야에 남는다. 또한 Pipeline만 잠그고 route inventory를 잠그지 않으면 validation traffic 뒤 Judge 입력이 변할 수 있다.

- **잠금:** `flowscope_lock_dataset`은 Pipeline 결과와 현재 route candidate list를 함께 불변 snapshot으로 보관한다. 잠금 뒤 도구는 snapshot만 반환하고 이후 state 변경을 따라가지 않는다.
- **검증:** HUMAN 관측+LLM 참조가 병합된 후보에서 Explorer view가 LLM provenance 하나, `observed=false`, `REVIEW`로 재계산되는지 확인한다. pre-lock cross-lane status와 ZAP/assessment/validation 접근 차단, lock 뒤 원본 route list를 바꿔도 반환 목록이 고정되는 회귀를 둔다.
- **한계:** Pipeline과 candidate publication은 현재 extension worker의 연속 갱신이며 하나의 transaction object는 아니다. lock은 호출 시점에 공개된 두 immutable snapshot을 잡는다. 실제 지연 응답과 rebuild 경합은 Burp runtime stress gate로 남긴다.
- **상태:** beta.6 구현·자동 회귀 완료, Burp/MCP 실환경 gate 대기.

## D-071 · 구독 LLM 버튼 실행 = 비영속 Explorer + 별도 지속 Judge

- **문제:** 수동 workspace 실행만으로는 사용자 개입이 크고 실행 프롬프트·target·run ID가 어긋날 수 있다. 반대로 Explorer와 Judge가 같은 provider 대화를 재사용하면 세 번째 lane의 독립성이 깨지고, CLI 프로세스 종료만 성공으로 믿으면 MCP run 미종료나 dataset 미잠금을 완료로 오인한다.
- **결정:** Web quick-start가 공급자·exact target·선택적 ACTIVE account를 받아 로컬 로그인 Codex/Claude CLI를 shell 없이 새 프로세스로 실행한다. Explorer는 전용 임시 작업공간에서 Codex ephemeral 또는 Claude no-persistence로 시작하며 이전 session ID를 입력·저장·resume하지 않는다. FlowScope가 exact LLM EXPLORATION run을 먼저 활성화하고 모델이 같은 run을 `flowscope_end_run`으로 끝낸 경우에만 LLM 완료 레인을 인정한다.
- **Judge 세션:** Judge는 세 완료 레인이 있어야 Explorer와 별개의 새 provider session으로 시작한다. 실제 MCP dataset lock이 확인돼야 성공한다. Codex JSON의 `thread_id` 또는 FlowScope가 선발급한 Claude `session-id`를 보존하고, 명시적인 `Judge 계속`만 exact ID로 resume한다. 이는 provider 대화의 논리적 지속이며 terminal 프로세스를 계속 살려 두는 구조가 아니다.
- **프로세스·비밀 경계:** 실행 파일은 시스템 속성 또는 Burp 시작 PATH의 regular executable만 허용하고 명령은 인자 배열로 전달한다. MCP Bearer는 자식 환경에만 두고 command line·prompt·project·공개 status에 넣지 않는다. 임시 workspace는 owner-only로 만들고 exact prefix를 확인한 뒤만 삭제한다. provider 출력은 secret masking과 64KiB 상한을 적용하며, 긴 Codex 출력에서도 첫 session event를 잃지 않도록 별도 8KiB prefix만 유지한다.
- **도구 경계:** Codex는 no-approval/read-only/user-config 무시와 동적 loopback MCP 설정을 사용한다. Claude는 strict 임시 MCP config와 역할별 exact MCP tool allowlist를 사용한다. 이 client-side 제한은 서버의 exact scope·Explorer visibility·Evidence/validation gate를 대체하지 않는다.
- **metadata 한계:** 일부 Claude Code 버전이 `--no-session-persistence`에도 ai-title/session metadata를 남길 수 있으므로 물리적 파일 0개를 주장하지 않는다. 고유 임시 cwd와 no-resume으로 논리적 오염을 막고 UI에 잔존 가능성을 표시한다. 다른 provider 작업을 손상할 수 있는 사용자 홈 광역 삭제는 기각한다.
- **상태 불변식:** locked dataset에는 새 Explorer를 시작할 수 없고, active run 또는 lock 중에는 Burp UI에서도 scope를 바꿀 수 없다. 같은 source의 새 exploration을 시작하면 이전 완료 표식을 즉시 무효화해 실패한 재실행의 부분 Evidence로 Judge가 열리지 않게 한다. 취소·실패 시 활성 LLM run을 abort하며, Judge follow-up은 lock이 사라지면 거부한다. UI도 세 완료 레인 전에는 Judge 버튼을 비활성화하지만 서버 gate가 최종 권위다.
- **가중치·판정:** 이 자동화는 탐색 실행과 Judge 전달을 줄이는 기능이지 새 confidence score나 판정 우회가 아니다. route 정렬은 기존 범주형 이유를 유지하고 최종 `CONFIRMED/REJECTED`는 기존 서버 Evidence gate만 결정한다.
- **검증·한계:** 실행 인자, no-resume, exact run 종료 실패, 3-lane/lock/account gate, Claude Judge resume, 긴 Codex session ID, Web API와 scope lock을 자동 회귀로 고정한다. 실제 사용자 구독 로그인, Burp-hosted MCP 왕복, 대상 요청, provider별 Judge follow-up은 beta.7 JAR 실환경 gate이며 자동 테스트로 통과했다고 주장하지 않는다.
- **상태:** beta.7 코드·자동 회귀 완료, Burp/Codex/Claude 실환경 gate 대기.

## D-072 · 로컬 LLM 실행 하드닝 = 사용자 기억 배제 + API key 비상속

- **문제:** 새 프로세스만 만든다고 독립성이 성립하지 않는다. Codex/Claude가 사용자 설정·프로젝트 지침·auto-memory를 읽거나, Burp 환경의 모델 API key를 상속하거나, Codex가 모델 shell에 MCP Bearer를 전달하면 구독 실행·closed-world·비밀 경계 주장이 깨진다. 취소와 child 등록 사이의 짧은 경합에서는 취소된 프로세스가 뒤늦게 계속 실행될 수도 있었다.
- **결정:** Codex는 `--ignore-user-config --strict-config`, 명시적 웹 검색 비활성화, read-only/no-approval과 `shell_environment_policy`의 `FLOWSCOPE_MCP_TOKEN` 제외를 적용한다. Claude는 `--setting-sources ''`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, strict 임시 MCP와 exact 역할 도구만 사용한다. 공통 child 환경에서 `OPENAI_API_KEY`·`ANTHROPIC_API_KEY`를 제거하며 provider OAuth/token 자체는 FlowScope가 읽지 않는다. 취소 또는 Burp unload 뒤 launcher가 반환한 child는 닫힘 상태를 다시 확인하고 즉시 종료한다.
- **경계:** 로컬 CLI 바이너리, provider 기본 system prompt, 관리자 강제 policy와 provider 측 metadata 저장까지 FlowScope가 제거한다고 주장하지 않는다. 따라서 독립성은 이전 FlowScope 대화·일반 사용자 설정·FlowScope cross-lane state를 재사용하지 않는 통제 경계이며, 모델의 수학적 완전 독립성 주장이 아니다.
- **검증:** 명령 인자·환경 필터·취소/unload-before-registration을 자동 회귀로 고정했다. 설치된 Codex CLI 0.147.0은 같은 격리 계열 옵션으로 무대상 `Reply exactly OK` 호출이 exit 0·정확한 `OK`를 반환했다. Claude Code 2.1.231은 옵션 파싱과 로그인 요청 단계까지 진입했으나 provider HTTP 429 주간 한도로 모델 응답을 받지 못했으므로 성공으로 기록하지 않는다. 둘 다 beta.7 Burp MCP/대상 E2E 검증을 대신하지 않는다.
- **상태:** 코드·자동 회귀·Codex 무대상 CLI smoke 완료. Claude 모델 호출과 beta.7 Burp-hosted MCP E2E 대기.

## D-073 · HUMAN Evidence 보존 = 전문·preview 분리 + 보조 흐름 비오염 표시

- **문제:** 기존 8KiB 단일 문자열은 query/body 뒤쪽 객체 ID, 긴 응답의 route 참조, 재현 근거를 조용히 잘랐다. 반대로 모든 전문을 무제한 평문으로 메모리에 두면 Burp 안정성과 비밀 경계가 깨진다. 또한 로그인·화면 이동·polling을 메인 인가 graph에서 빼기만 하면 사용자는 실제로 관측됐는지 확인할 수 없고, 다시 포함하면 coverage와 gap이 오염된다.
- **저장 결정:** header와 구조화 body를 먼저 마스킹한 textual 요청·응답 전문을 메시지당 기본 1MiB, digest 중복 제거 후 압축 총량 48MiB까지 GZIP으로 보존한다. record는 SHA-256·원 byte 수·retention을 들고, project schema v2는 같은 digest blob을 한 번만 저장한다. 8KiB 필드는 UI preview로만 유지한다. binary와 메시지별/총량 상한 초과 전문은 내용 없이 size+digest+사유만 남기며 UI가 metadata-only임을 표시한다. schema v1은 계속 읽지만 과거에 저장되지 않은 전문을 복원한 것처럼 꾸미지 않는다.
- **자원 결정:** path와 모든 명시 query/중첩 JSON·배열/XML/multipart/GraphQL ID 참조를 `ResourceReference`로 보존한다. 현재 인가 cell은 Evidence 순서의 첫 참조만 primary로 사용한다. operation별 객체 적용 가능성 없이 모든 참조를 Cartesian product로 펼치는 방식은 오탐을 만들므로 기각한다.
- **노이즈 결정:** `SESSION_SETUP`은 `AUTH_SESSION/EXCLUDE`, 반복 안정 unknown은 `POLLING/REVIEW`로 구분한다. 메인 graph·coverage·gap은 계속 `INCLUDE`만 사용한다. 사용자가 켠 경우에만 인증·navigation·polling·background를 중립 보조 레이어로 그리며 이 edge는 cell/verdict/finding을 만들지 않는다. source 필터는 edge뿐 아니라 해당 source만 가진 node도 숨긴다.
- **샘플 경계:** 고정 `demo.flowscope.test`와 `demo-*` run만 있는 합성 dataset은 snapshot에서 명시적으로 식별하고 Web에 “실제 점검 결과 아님·네트워크 요청 0건”을 지속 표시한다. H/S/L 모양만으로 실제 Burp Browser·ZAP·Codex 실행을 암시하는 표시는 기각한다.
- **용량 경계:** live record 20,000건과 digest 중복 제거 후 압축 전문 총량 48MiB 상한을 beta에서 유지한다. record 초과분은 dropped count와 “현재 분석은 불완전” 경고로, 전문 총량 초과분은 metadata-only 메시지 수와 개별 사유로 snapshot/Web에 노출한다. project 저장 결과가 100MiB를 넘으면 교체 전에 거부한다. 무제한 RAM, silent truncation, raw secret 저장, 검증되지 않은 임의 가중치는 기각한다. 장시간·대용량 engagement용 disk-backed event store는 별도 성능 gate 뒤 후속 단계다.
- **검증·한계:** 압축 round-trip·digest 손상·binary/over-limit·schema v1/v2·blob dedup·중첩/복수 객체·인증/polling 분류 회귀를 추가한다. 자동 회귀와 standalone 브라우저 검증은 실제 Burp Browser의 장시간 메모리·20,000건 초과·저장/복구 gate를 대신하지 않는다.
- **상태:** beta.8 코드·183개 자동 회귀·standalone UI 완료, 실제 Burp Community 장시간 수집은 수동 gate.

## D-074 · raw URL 보존 + Evidence 단계형 operation template
- **문제:** 모든 숫자 세그먼트를 즉시 `{id}`로 바꾸면 `/status/200`, `/top/10` 같은 literal 경로를 오병합한다. 반대로 전부 literal로 두면 `/orders/101`과 `/orders/202`가 같은 operation임을 비교할 수 없다. 블랙박스 트래픽만으로 서버의 실제 route declaration을 완전히 복원할 수는 없다.
- **결정:** raw path는 항상 보존하고 operation 묶음만 별도로 계산한다. `CORROBORATED`는 2xx JSON 응답의 동일 ID 값, `INFERRED`는 UUID/16자 이상 hex 형식 또는 같은 service·구조·위치의 복수 값/독립 관측 반복, `LITERAL`은 승격 근거 없음이다. route declaration을 보지 않은 형식 추론을 “확정”이라 부르지 않는다. 확률이나 임의 가중치는 쓰지 않고 범주형 이유를 함께 노출한다.
- **객체와 template 분리:** `/orders/101`의 객체 후보 `orders:101`은 단일 관측에서도 보존한다. operation을 literal로 두는 보수성이 인가 분석의 객체 축을 지우지 않게 하기 위해서다.
- **자동화 경계:** 근거는 같은 service와 구조에만 전파하고 method는 공유한다. 사용자는 정상 흐름에서 승인 작업을 하지 않으며 상세 화면에서 원문·상태·이유를 감사한다. 서버 명세/OpenAPI가 관측된 경우 이를 별도 강한 route oracle로 쓰는 것은 후속 범위다.
- **근거:** OpenAPI 3.0.4는 path templating과 concrete path 우선순위를 정의하지만 ambiguous matching은 tooling-defined라고 명시한다. Burp Compare Site Maps도 path/method/parameter 기준 비교가 false match를 만들 수 있다고 경고한다. mitmproxy2swagger 역시 concrete/template 후보를 검토 가능한 형태로 유지한다. 따라서 raw 보존 + 근거 노출이 자동 묶음만 신뢰하는 것보다 감사 가능하다.
- **참고:** [OpenAPI 3.0.4 Paths](https://spec.openapis.org/oas/v3.0.4.html#paths-object), [Burp Compare site maps](https://portswigger.net/burp/documentation/desktop/tools/target/site-map/comparing), [mitmproxy2swagger](https://github.com/alufers/mitmproxy2swagger)
- **한계:** 복수 값 반복은 route declaration의 증명이 아니므로 `INFERRED`다. 실제 blind-target 정확도는 독립 corpus/실대상 검증 전까지 주장하지 않는다.

## D-075 · 로컬 내구 저장과 세션 표현 = SQLite snapshot + account projection

- **문제:** `.flowscope.json` 수동 저장만으로는 Burp 종료·충돌 전에 최신 변경을 놓칠 수 있고, 장래 self-host 방향에서 record·payload·account·판정을 모두 한 JSON 문서로만 다루기 어렵다. 동시에 Web이 Cookie, Authorization, JWT subject 지문을 같은 수준의 행으로 나열해 한 `test1` 로그인이 세 계정처럼 보였다.
- **저장 결정:** 기본 프로젝트는 로컬 `.flowscope.db`다. SQLite storage schema v1은 metadata/migration과 records, digest-deduplicated payload BLOB, accounts, service-scoped session bindings, policy, reviews, assessments, validations, completed lanes, route candidates를 관계형 테이블로 나눈다. 기존 JSON schema v2 codec을 공통 유효성·마스킹·round-trip 경계로 재사용하고 JSON v1/v2 읽기와 v2 내보내기를 유지한다. 사용자가 DB를 한 번 저장하거나 열면 revision 변경을 30초 checkpoint로 합쳐 transaction으로 임시 DB에 쓴 뒤 atomic replace하고, 정상 unload 직전 마지막 저장을 시도한다. 전체 snapshot을 매초 재작성하는 안은 디스크·CPU 비용 때문에 기각했다.
- **비밀·자원 경계:** raw Cookie/Authorization/CSRF는 계속 `SessionBroker` 메모리에만 있고 SQLite/JSON 어느 쪽에도 저장하지 않는다. DB는 100MiB, live pipeline은 20,000 record·압축 전문 48MiB 상한을 그대로 적용한다. 현재 방식은 메모리 상태의 내구 snapshot이며 append-only event ingestion이나 다중 사용자 서버 DB가 아니다. 서버 확장은 실제 부하·마이그레이션·동시성 측정 뒤 별도 결정한다.
- **화면 결정:** 기본 계정 화면은 `AccountProfile` 하나를 카드 하나로 표시하고 broker 상태를 `로그인 필요/확인 중/사용 가능/다시 로그인 필요`와 다음 행동으로 번역한다. 계정에 연결된 Cookie/token/subject 비가역 지문은 접힌 기술 정보에만 묶고, 미연결 지문만 고급 세션 진단에서 수동 연결한다. 수집 원시성은 유지하되 사용자에게 내부 artifact를 principal처럼 표시하지 않는다.
- **기각:** fingerprint 행 자체를 삭제하면 회전·충돌·수동 복구 Evidence를 잃는다. 자동으로 비슷한 지문을 계정에 병합하면 다른 사용자를 합칠 수 있다. SQLite를 즉시 live source of truth나 원격 서버 backend로 만드는 것은 현재 single-worker pipeline과 검증되지 않은 성능 범위를 넘어 기각했다.
- **검증·한계:** SQLite header, 관계형 row, payload dedup/round-trip, raw secret 부재, 미지원 storage schema 거부, 세 artifact가 한 account ID로 projection되는 회귀를 추가한다. xerial SQLite JDBC의 native load는 현재 자동 JDK에서 경고와 함께 성공했지만 beta.10 fat JAR의 Burp bundled JVM 실제 저장·재열기는 별도 수동 gate다.

## D-076 · 메인 접근 그래프 = source 전체 경로, 데이터 의존성 = 별도 화면

- **문제:** beta.10의 source 필터는 edge 표시만 바꿔 0건 SCANNER/LLM도 동작 가능한 필터처럼 보였고, 객체 경유 경로의 한 구간은 source 문법이 적용되지 않아 선의 출처가 불명확했다. 응답→요청 데이터 의존선까지 같은 canvas에 겹치면서 HUMAN만 선택한 화면에도 옅고 끊긴 듯한 선이 남았다. 그래프 레일의 역할 클릭은 API 요구 권한이 없는 상태에서도 계정 역할을 순환·저장해 BFLA 정책 입력 위치를 혼동시켰다.
- **결정:** source별 `coverageEligible` Evidence 수를 필터 옆에 표시하고 0건 source는 비활성화한다. 필터 변경 시 graph를 다시 만들어 해당 source만 가진 node와 `identity → resource → operation` 두 접근 구간을 함께 제거한다. 두 구간 모두 D-061의 색·선형·문자 문법을 적용한다. 응답→요청 ID/token 의존성은 D-043의 `흐름 순서`에서만 표시한다. 그래프 레일은 계정 역할과 API 요구 권한 개수를 읽기 전용으로 요약하며, 역할은 `계정·세션`, 요구 권한은 API 상세에서만 수정한다.
- **기각:** 객체→API 구간만 source 색으로 칠하면 경로 시작점의 출처가 다시 중립으로 남는다. 데이터 의존선을 범례만 추가해 메인 graph에 유지하면 접근 관계와 값 전달 관계라는 서로 다른 edge 의미가 한 화면에 계속 섞인다. 그래프 문맥 없는 역할 순환은 입력이 빠르지만 오조작과 정책 출처 불명을 만든다.
- **호환:** 분석·coverage·gap·verdict 계산은 바꾸지 않는다. 이전 수동 node 위치가 제거된 edge 의미를 전제로 하므로 local graph-state key를 v3으로 올려 새 배치를 사용한다.
- **검증·한계:** Web 정적 계약은 source 수량·0건 비활성·필터 재구축·전체 경로 source 문법·flow edge 부재·role cycle 부재를 검사한다. standalone 렌더와 실제 Burp beta.11 재로드는 각각 완료 결과를 `beta-validation.md`에 기록하며, 이 UI 수정은 탐지율 개선이나 오탐·미탐 0의 근거가 아니다.

## D-077 · 계정 귀속과 그래프 중복 = 엔진은 유일성, 화면은 비파괴 집계

- **문제:** `(service, fingerprint)` binding을 단순 덮어쓰면 USER A의 동일 인증정보를 USER B에 다시 등록하는 순간 과거 신원 귀속이 조용히 바뀐다. 그래프에서는 같은 요청자·객체·source가 여러 operation을 호출할 때 접근선이 같은 좌표에 중첩되고, 긴 operation을 중간 생략해 사용자가 선과 경로를 구분하기 어려웠다.
- **세션 결정:** service-scoped fingerprint는 한 account에만 연결한다. 다른 account로의 두 번째 binding은 예외로 거부하고, 해당 로그인 캡처 broker session을 `SUSPECT` 충돌 상태로 고정해 이후 응답이 와도 `ACTIVE`로 돌아가지 않게 한다. 충돌 세션은 요청 자격증명 신원 매칭과 세션 주입에서 제외한다. 명시적으로 기존 연결을 해제한 뒤 재연결하는 절차만 허용한다.
- **그래프 결정:** 동일 `(identity, resource, source)`의 `identity → resource` 접근선만 표시 집계한다. 총 관측 수와 원 CoverageCell 키 전체를 edge data에 보존하고, 클릭하면 operation별 관측 수·verdict·gap을 나열해 기존 cell/Evidence 상세로 이동한다. `resource → operation` 선과 Java의 coverage/gap/verdict 모델은 변경하지 않는다. 객체 없는 `identity → operation`은 이미 cell당 하나이므로 기존 반복 count만 유지한다.
- **라벨 결정:** operation/resource 원문은 중간 생략하지 않고 문자 단위 줄바꿈과 내용 기반 node 높이를 사용한다. Cytoscape canvas의 최소 논리 폭과 identity/source 기반 taxi turn을 적용해 같은 좌표의 선을 구분하되, force layout·새 그래프 라이브러리·전체 UI 재설계는 이번 범위에서 도입하지 않는다.
- **기각:** 화면에서 중복 계정 카드만 숨기면 저장 binding과 broker 귀속 오염이 남는다. 동일 객체의 모든 operation을 하나의 coverage cell로 합치면 판정과 Evidence 단위가 손실된다. 긴 경로를 tooltip에만 남기고 계속 생략하면 screenshot·발표·비교 시 경로가 보이지 않는다. Dagre/ELK로 전체 배치를 교체하는 안은 현재 결함보다 변경 범위와 회귀 위험이 커 후속 대규모 그래프 성능 측정 전에는 채택하지 않는다.
- **검증·한계:** 두 번째 binding 거부, 충돌 상태 비활성·비재활성, 기존 account 신원 매칭 유지, Web 집계·원키·상세·줄바꿈 계약을 자동 회귀로 고정한다. standalone 샘플에서 렌더와 console을 확인한다. 집계는 표시 중복을 줄일 뿐 endpoint 발견률이나 판정 정확도를 높이지 않으며, 전체 edge crossing 최소화 문제를 해결했다고 주장하지 않는다. 실제 beta.12 Burp 재로드와 복수 계정 충돌 흐름은 수동 gate다.
- **상태:** beta.12 코드·자동 회귀·standalone 검증 완료, Burp 수동 gate 대기.

## D-078 · 완성 목표 = 관측 가능한 공격면 구조화 + Evidence 기반 검증

- **문제:** 기능 목록과 UI 구현 여부만으로 제품 완성을 판단하면 블랙박스에서 알 수 없는 전체 공격면, 오탐·미탐 0, LLM 자동 확정 같은 검증 불가능한 주장을 만들 수 있다. 반대로 한계를 나열하기만 하면 실제로 무엇을 개선하고 측정해야 하는지도 불명확하다.
- **결정:** FlowScope의 정본 목표는 허가된 exact scope에서 관측 가능한 접근통제 공격면을 최대한 구조화하고, 신원·작업·객체·상태 흐름의 차이를 재현 가능한 Evidence로 검증해 사람이 놓치기 쉬운 경로와 인가 후보를 드러내는 것이다.

- **비목표:** 모든 endpoint·객체·상태 발견, 오탐·미탐 0, LLM 서술만으로 최종 확정, 자동화 단계 종료나 HTTP 상태만으로 점검 충분성을 판정하는 주장은 기각한다.
- **호환:** 기존 exact-scope, source/identity 분리, 후보/관측 분리, 서버 Evidence gate, 커버리지 퍼센트 금지 계약을 바꾸지 않는다. 제품 코드와 저장 schema 변경은 없다.
- **상태:** 마스터 계획 1단계 문서 계약 완료. 우선순위 원칙은 다음 단계에서 별도로 검토한다.

## D-079 · HUMAN 범용 구조 파악 = exact run + 보수적 semantic field 보강

- **문제:** 수집 건수가 있다는 사실을 HUMAN pass 완료로 표시하면 pass 밖 과거 Evidence도 완료처럼 보이고, 활성 pass 안의 Repeater·Intruder 요청을 run context의 `BROWSER`로 덮으면 실제 수행 도구 provenance가 사라진다. 또한 `id/*Id`만 객체로 읽으면 `customerNo`, `documentSeq`, `accountRef`처럼 서비스마다 다른 식별자 명명법을 놓치지만, `*No/*Key` 이름만 보고 모두 객체화하면 `pageNo`, `sortKey`, API key 같은 제어·보안 필드가 graph를 오염시킨다.
- **결정:** HUMAN Web 상태는 다른 실행 상태와 함께 주기적으로 조회하고, 완료는 `RunContextRegistry`가 exact `EXPLORATION` run을 같은 run ID로 종료했을 때만 표시한다. run context는 orchestrator/phase/run/account를 제공하되, Burp Repeater·Intruder·Target 관측의 source detail과 `BURP` tool은 유지한다. 비-`*Id` 객체 후보는 target 이름이나 path 사전 없이 query·JSON/form body의 도메인 중립 suffix를 읽고, 같은 service·method·raw path·field 위치에서 서로 다른 값이 둘 이상 관측된 경우에만 `*_SEMANTIC_FIELD_CORROBORATED`로 승격한다.
- **제외:** `page/sort/status/error/request/trace/correlation`과 API/auth/token/session/secret류, 마스킹 값, 256자를 넘는 값, 단일 관측은 자동 객체로 만들지 않는다. 일반 `*Code`는 상태·enum과 충돌이 많아 이 단계에서 후보 suffix로 채택하지 않는다. 명시 ID도 `id`, camel-case `*Id/*Ids`, snake/kebab `*_id/*_ids` 경계만 강하게 인정하고 `guid/valid/fluid` 같은 일반 소문자 단어의 끝 두 글자를 ID로 보지 않는다. semantic reference도 기존 복수 참조와 같이 첫 근거 하나만 primary이며 객체 Cartesian product를 만들지 않는다.
- **기각:** 대상별 crAPI/네이버/WebSquare 필드 사전은 일반 도구 목적과 블라인드 benchmark를 오염시켜 기각했다. LLM이 모든 필드를 즉시 판정하는 방식은 비결정적이고 원 Evidence 없이 결과가 바뀔 수 있어 핵심 수집기에 넣지 않는다. 이름 하나만으로 승격하거나 서로 다른 endpoint의 같은 필드명을 합치는 방식도 오탐 전파 때문에 기각했다.
- **한계:** 이 규칙은 관측된 값의 식별자 가능성을 보강할 뿐 실제 route schema, 소유권, 인가 취약점을 증명하지 않는다. 동적 JavaScript에서 아직 전송되지 않은 값과 한 번만 관측된 도메인 식별자는 자동 확정할 수 없다. 다양한 blind target에서 field-level precision/recall과 REVIEW 비용을 측정하기 전 성능 우위를 주장하지 않는다.
- **상태:** beta.13 구현·204개 자동 회귀·standalone HUMAN 상태 전이 검증 완료, 실제 Burp Browser/Repeater/Intruder와 블라인드 corpus gate 대기.

## D-080 · ZAP 완료 gate = raw capture, 화면 상태 = 신원·단계별 projection

- **문제:** Burp 응답 callback은 raw record를 즉시 저장하지만 분석 `Pipeline.Result` 재빌드는 400ms debounce된다. ZAP spider와 passive queue가 먼저 종료된 직후 분석 snapshot만 세면 실제 SCANNER 응답이 raw store에 있어도 신원별 capture가 0으로 보여 정상 캠페인을 실패 처리할 수 있다. 기존 Web 상태 한 줄은 어느 신원의 Traditional/Client/AJAX 단계가 실제 트래픽을 만들었는지 구분하지 못했다.
- **결정:** 캠페인 완료, zero-capture, global/lane capture 수의 정본은 raw record 저장소의 `source + runId + sourceDetail` count다. 일반 MCP 테스트·standalone 구현은 현재 snapshot 기반 default를 쓰되 Burp 확장은 synchronized raw store 구현을 제공한다. 신원별 상태는 전체, Traditional, Client/AJAX rendered capture와 Alert, warning, error를 분리해 Web/MCP에 projection한다.
- **기각:** 임의 500ms sleep 뒤 snapshot을 다시 읽는 방식은 부하·스케줄러에 따라 다시 실패하고 테스트를 느리게 만들어 기각했다. Pipeline debounce를 제거하는 방식은 Burp callback마다 전체 분석을 실행해 UI·메모리 보호 계약을 훼손한다. 화면 한 줄에 모든 lane을 이어 붙이는 방식은 실패 신원과 단계를 찾기 어려워 기각했다.
- **근거:** FlowScope의 실제 수집 코드에서 raw append와 400ms scheduled rebuild의 시간차를 확인했고 stale snapshot/raw capture fixture로 회귀를 고정했다. ZAP 공식 문서는 Client Spider status 100을 crawl 완료로, passive scan은 별도 background queue로 설명하므로 crawl 종료·passive drain·FlowScope capture 존재를 서로 다른 gate로 유지한다.
- **한계:** raw count는 FlowScope가 응답을 관측했다는 증거이지 endpoint 충분성이나 취약점 발견 성능의 증거가 아니다. 실제 ZAP/Burp 네트워크에서 아주 늦은 응답, Client Spider browser add-on, USER A/B 주입은 beta.14 JAR 수동 gate로 남는다.
- **상태:** beta.14 구현·206개 자동 회귀 완료, 실제 Burp/ZAP 복수 신원 gate 대기.

## D-081 · rendered crawler 완료 gate = ZAP 상태가 아니라 실제 단계 capture

- **문제:** 실제 ZAP 2.17 + crAPI 실행에서 Client Spider의 Firefox browser binary가 없어 task가 내부 실패했지만 Client API status는 `100`을 반환했다. beta.14는 API 호출 예외만 AJAX fallback 조건으로 사용해 `rendered_captures=0`인 lane도 전체 Traditional capture가 있으면 깨끗한 `COMPLETED`로 표시했다.
- **결정:** Client status 종료 뒤 같은 run·lane의 raw `ZAP_CLIENT_SPIDER` capture 증가가 0이면 Client 실행을 rendered discovery 불가로 간주하고 AJAX Spider를 자동 실행한다. AJAX도 raw capture 증가가 0이면 Traditional Evidence와 native Alert는 보존하고 scanner exploration 완료 표식도 유지하되, lane과 캠페인 status를 `COMPLETED_WITH_WARNINGS`로 표시하며 두 단계의 zero-capture 원인을 노출한다. 전체 scanner capture가 0인 기존 failure gate는 유지한다. 경고 완료도 dataset lock 뒤에는 실행 시점의 마스킹 Alert snapshot만 제공해 Judge 입력을 고정한다.
- **기각:** ZAP status `100`만 믿는 방식은 재현된 거짓 정상 완료를 숨겨 기각했다. ZAP 로그 문자열이나 OS별 Firefox 경로를 FlowScope가 파싱·강제하는 방식은 add-on·브라우저 provider·운영체제 결합도가 높아 기각했다. rendered 0일 때 Traditional 결과까지 실패·폐기하는 방식은 실제 수집 Evidence를 잃어 기각했다.
- **한계:** raw capture 0은 browser task가 유효한 rendered 요청을 만들지 못했다는 관측이지 정확한 원인 진단은 아니다. 동일 URL 캐시, 대상 동작, ZAP provider 설정 등도 원인이 될 수 있으므로 UI는 Firefox 부재를 일반화하지 않고 실제 로컬 검증 기록에서만 그 원인을 적는다. beta.15 JAR의 실제 Client→AJAX 전환과 rendered capture는 재로드 후 수동 gate다.

## D-082 · HUMAN 요청 문맥 = response 시점 추정 금지 + 데이터셋 세대 격리

- **문제:** Proxy 응답은 이미 Montoya `messageId`로 요청 시점의 run/account를 보존했지만, Repeater·Intruder·Target 등 비-Proxy 응답은 응답이 도착한 순간의 활성 HUMAN context를 읽었다. pass 중 보낸 요청이 종료 뒤 도착하면 BASELINE으로 빠지고, pass 전에 보낸 요청이 시작 뒤 도착하면 해당 pass로 잘못 들어갈 수 있었다. 초기화·샘플 교체·프로젝트 열기 직전의 in-flight 응답도 새 데이터셋을 다시 채울 수 있었다.
- **결정:** Proxy와 비-Proxy Burp 도구에 각각 bounded in-flight tracker를 두고, 공식 Montoya 요청·응답의 동일 `messageId()`로 요청 시점 context, 로그인 캡처 account, 데이터셋 epoch를 연결한다. 응답은 저장 직전 epoch를 다시 확인하며, 초기화·샘플 교체·프로젝트 열기는 records lock 안에서 epoch를 증가시킨다. 대응 요청 문맥이 없거나 epoch가 다르면 현재 context로 추측하지 않고 응답을 수집에서 제외한다. 비-Proxy HUMAN 응답도 성공적으로 수집됐을 때만 broker에 전달해 Repeater에서 생긴 쿠키 회전을 같은 메모리 세션에 반영한다.
- **표현 결정:** 권한 정책 카드의 신원 한 줄은 `등록 계정/비로그인/미확정 신원/관측 신원`만 표시한다. Cookie·Authorization·subject fingerprint 개수는 로그인 세션 수가 아니므로 `세션 N개`로 표시하지 않고 계정 화면의 접힌 기술 정보에만 남긴다.
- **기각:** 응답 시점의 활성 pass로 fallback하면 조용한 오귀속이 생긴다. 데이터셋 교체 때 tracker를 단순 삭제하면 이미 전송된 응답이 문맥 없음 fallback으로 다시 들어온다. 반대로 모든 in-flight payload를 복제하면 메모리 비용이 커진다. 따라서 작은 context metadata만 최대 20,000건·10분 TTL로 보존하고 상한 초과는 fail-closed한다.
- **근거:** 로컬 의존성의 Montoya API 2026.7 `HttpRequestToBeSent`와 `HttpResponseReceived`가 모두 `int messageId()`를 제공함을 확인했다. tracker correlation·epoch·capacity·TTL과 Web 표현 계약을 자동 회귀로 고정했다.
- **한계:** 확장 로드 전에 이미 전송됐거나 tracker 상한을 넘은 요청의 응답은 정확한 요청 시점 문맥을 복원할 수 없어 버린다. beta.16 실제 Burp Browser/Repeater late-response와 초기화 직후 응답 gate는 JAR 재로드 뒤 수동 검증해야 한다.
- **상태:** beta.16 코드·211개 자동 회귀·단일 JAR 무결성 완료, 실제 Burp 수동 gate 대기.

## D-083 · HUMAN 수동 검증 = bounded raw vault + Web 요청 실험실 + discovery 분리

- **문제:** 기존 Web은 마스킹된 Evidence를 보여 주고 Burp Repeater 초안만 열었다. 보안 진단자는 Cookie·Authorization·body·object 값을 직접 비교·변경하고 응답을 나란히 확인해야 하므로 이 경계만으로는 Web 작업면이 실제 검증 도구가 아니었다. 반대로 raw 인증값을 `RequestRecord`나 SQLite/JSON에 넣으면 기존 비밀 비영속 계약을 깨고, 변조 요청을 HUMAN 탐색 성과로 세면 커버리지도 오염된다.
- **결정:** live 요청·응답 원문은 `TransientExchangeVault`의 byte 상한(요청 1MiB, 응답 4MiB, 합계 32MiB) 안에서 Burp 프로세스 메모리에만 둔다. 특정 Evidence를 명시적으로 선택했을 때만 localhost capability API와 현재 탭으로 전달한다. Web 요청 실험실은 원문 편집기·응답 뷰·탭 메모리 10건 이력과 `ORIGINAL/ANONYMOUS/ACCOUNT` 모드를 제공한다. 대상 `HttpService`는 원 Evidence에 고정하고 exact scope 재검사, redirect 금지, TLS 검증, 30초 timeout을 적용한다. 결과는 HUMAN `MANUAL_HTTP/VALIDATION/CONTROLLED` Evidence로 새로 기록하되 immutable discovery gate로 coverage·gap에서 제외한다. Repeater 미전송 handoff는 fallback으로 유지한다.
- **인증 모드:** `ORIGINAL`은 사용자가 편집한 헤더를 그대로 보낸다. `ANONYMOUS`는 broker가 관리하는 Authorization/Cookie/Proxy-Authorization/CSRF를 제거한다. `ACCOUNT`는 같은 헤더를 제거한 뒤 선택한 ACTIVE 계정의 service/path 적용 가능한 현재 값을 주입한다. 기존 `Content-Length`는 body byte 길이로 갱신한다.
- **기각:** 마스킹값만 편집하게 하면 실제 세션·인가 검증을 할 수 없어 기각했다. raw를 프로젝트/브라우저 localStorage에 저장하는 방식은 노출 수명과 복제 범위를 넓혀 기각했다. 브라우저 fetch로 대상에 직접 보내는 방식은 CORS·프록시·TLS·Evidence 상관을 잃어 기각했다. 모든 전송을 discovery로 세는 방식은 사람이 반복한 검증 횟수를 탐색 커버리지로 오표시해 기각했다. 기능을 Burp Repeater에만 두는 방식은 Web에서 요청·응답 비교를 원하는 제품 UX를 충족하지 못해 fallback으로만 남겼다.
- **근거:** PortSwigger 공식 Repeater·message editor·HTTP history 문서는 요청 편집/재전송, 응답 비교, history·timing을 수동 검증의 기본 흐름으로 정의한다. ZAP 공식 Requester도 기존 요청 편집·재전송과 다중 탭/응답 시간·크기를 제공한다. mitmproxy 공식 client replay 역시 저장 flow 수정·재전송을 제공한다. OWASP WSTG session fixation 절차는 별도 계정·쿠키 변경을 통한 대조가 필요함을 명시한다. 구현 API는 로컬 Montoya 2026.7의 `HttpRequest.httpRequest(HttpService,String)`, `Http.sendRequest`, `RequestOptions`를 확인했다. 참고: [Burp Repeater](https://portswigger.net/burp/documentation/desktop/tools/repeater), [Burp message editor](https://portswigger.net/burp/documentation/desktop/tools/message-editor), [Burp HTTP history](https://portswigger.net/burp/documentation/desktop/tools/proxy/http-history), [ZAP Requester](https://www.zaproxy.org/docs/desktop/addons/requester/), [mitmproxy client replay](https://docs.mitmproxy.org/stable/mitmproxytutorial-replayrequests/), [OWASP WSTG session fixation](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/06-Session_Management_Testing/03-Testing_for_Session_Fixation).
- **한계:** Java `String`, HTTP library, browser textarea에 생긴 복사본의 완전한 메모리 소거는 보장하지 않는다. raw vault는 확장 unload·데이터셋 교체 시 폐기되지만 crash dump/swap 방어를 주장하지 않는다. 가져온 프로젝트/XML·binary·상한 초과 항목에는 raw가 없어 마스킹 전문만 표시한다. 현재 자동 회귀는 저장 경계와 HTTP API 계약을 검증했지만 실제 Burp의 ORIGINAL/ANONYMOUS/ACCOUNT 전송은 beta.17 JAR 재로드 뒤 별도 수동 gate다.
- **상태:** beta.17 코드·215개 자동 회귀·standalone 반응형 UI·단일 JAR 무결성 완료, 실제 Burp ORIGINAL/ANONYMOUS/ACCOUNT 수동 gate 대기.

### D-084. HTTP 바이트가 정본이며, 화면 표현은 손실 없는 경우에만 편집 가능하다

- **결정:** live Evidence의 canonical 원문은 Java `String`이 아니라 Montoya가 제공한 요청·응답 바이트와 body offset이다. HTTP 헤더는 ISO-8859-1로, textual body는 Content-Type의 명시 charset 또는 JSON을 포함한 기본 UTF-8로 `REPORT` 오류 정책을 사용해 디코딩한다. 수정하지 않은 요청과 Repeater 초안은 원래 바이트 그대로 구성한다. 편집한 텍스트만 선언 charset으로 엄격히 재인코딩하며 binary·지원하지 않는 charset·잘못된 byte sequence는 Web 전송을 막고 원문 byte 보존과 Burp Repeater 경로만 유지한다.
- **UI 결정:** 긴 operation은 `/` 경계를 우선해 줄바꿈하고 단일 접근선에는 횟수 라벨을 붙이지 않는다. 900px 이하에서는 캔버스를 축소해 가리는 대신 현재 source·identity 필터가 적용된 API 목록으로 전환한다. 파싱 표의 행 전체 클릭에 의존하지 않고 Evidence별 `상세 보기` 버튼으로 정확한 ID를 선택해 해당 요청·응답을 연다. 그래프의 `관측 신원`과 Session Broker의 `재사용할 등록 계정`은 이름과 상태를 분리한다.
- **근거:** Montoya `ByteArray.getBytes()`와 `HttpRequest.toByteArray()/bodyOffset()`은 원문 byte 경계를 제공한다. RFC 8259의 interoperable JSON 기본 인코딩은 UTF-8이며, Content-Type charset은 명시된 legacy textual body의 디코딩 근거다. replacement character가 들어간 텍스트를 재전송하면 원 Evidence와 다른 요청을 만들므로 오류를 숨기지 않는 strict codec이 필요하다. 좁은 캔버스 축소는 노드 가독성과 클릭 대상을 동시에 잃지만, 동일 필터의 목록은 데이터 의미를 바꾸지 않고 읽기·선택을 보존한다.
- **기각:** 모든 메시지를 `toString()` 후 UTF-8로 다시 저장, 디코딩 실패를 replacement character로 숨김, binary를 textarea에서 편집, 좁은 화면에서 최소 폭 캔버스를 화면 밖으로 넘김, 행 어디든 클릭하면 임의의 같은-operation Evidence를 여는 방식, 관측된 신원이 곧 재사용 가능한 ACTIVE 세션이라고 표현하는 방식을 기각했다.
- **한계:** beta.17까지 이미 손실된 String Evidence는 원래 byte로 복원할 수 없어 beta.18 재로드 뒤 재수집해야 한다. 프로젝트/XML에서 가져온 항목, raw 상한 초과 항목, binary/해독 불가 body는 Web 편집 전송 대상이 아니다. 자동 회귀는 byte·codec·Web 계약을 검증했고 standalone UI는 1280px/600px에서 확인했지만, 실제 Burp target에 대한 ORIGINAL/ANONYMOUS/ACCOUNT 수신 byte 비교는 beta.18 JAR 재로드 뒤 수동 gate다.
- **상태:** beta.18 코드·221개 자동 회귀·standalone 반응형/선택 UI 검증 완료. 실제 Burp byte replay와 등록 계정 전송 gate 대기.

## D-086 · 공개 실행 환경 = host Burp/구독 CLI + 선택형 Docker ZAP

- **문제:** README가 Release JAR 사용과 소스 빌드 요구사항을 섞고, 완전한 3-way에서도 ZAP·LLM을 단순 선택 항목처럼 표현했다. 사용자가 ZAP API key, Docker-host 주소, Burp upstream proxy를 직접 조립하면 ZAP은 떠 있어도 대상 트래픽이 SCANNER `8081`을 통과하지 않는 조용한 실패가 생긴다.
- **결정:** 완전한 3-way의 필수 구성은 Burp, ZAP 2.17.0, 로그인된 Codex CLI 또는 Claude Code 하나로 명시한다. Release JAR 사용자는 Maven이 필요 없고 소스 빌드에만 JDK 21/Maven 3.9를 요구한다. Burp와 provider CLI는 host-native로 유지하고, ZAP만 digest 고정 공식 이미지를 선택형 Compose로 제공한다. macOS/Linux helper는 random key를 owner-only 기본 파일에 만들고 공식 ZAP Network API로 `host.docker.internal:<SCANNER port>` upstream을 설정·재조회한다. API publish는 host loopback으로 제한한다.
- **secret 경계:** FlowScope는 `flowscope.zap.key` → `FLOWSCOPE_ZAP_API_KEY` → `flowscope.zap.keyFile` → `~/.flowscope/zap-api-key` 순으로 해석한다. 파일은 링크 추적 없이 512 bytes 이하, URL-safe 32~256자, POSIX owner-only만 허용한다. Compose에는 key 값을 환경변수로 넘기지 않고 owner-only 파일을 컨테이너에 read-only mount한다. key는 저장소·프로젝트·MCP·Web snapshot에 넣지 않는다.
- **기각:** Burp와 구독 CLI를 함께 컨테이너화하는 방식은 GUI/Montoya와 사용자 로그인·keychain·PATH 경계를 불필요하게 복잡하게 만들어 기각했다. ZAP API key를 끄거나 저장소에 공용 key를 커밋하는 방식도 로컬 웹페이지에 의한 API 호출 위험과 secret 재사용 때문에 기각했다. floating `stable` 이미지는 core와 add-on 재현성이 월별로 달라져 2.17.0 manifest digest를 사용한다.
- **한계:** helper와 doctor는 macOS/Linux Bash에서만 검증했다. Windows는 동일 Compose의 수동 PowerShell 절차를 제공하지만 자동화 완료로 주장하지 않는다. container health/API/upstream/add-on 확인은 실제 target TLS, USER A/B 주입, Client/AJAX rendered capture, 취약점 탐지 성능을 증명하지 않는다.

## D-090 · fat JAR 격리·라이선스·재현성 = 의존성별 위험에 맞춘 검증

- **문제:** 모든 dependency의 `META-INF/NOTICE`를 제거해 Jackson의 Apache NOTICE가 배포물에서 사라졌고, 프로젝트 NOTICE는 SnakeYAML을 FasterXML 저작물처럼 묶었다. Java-only jsoup·SnakeYAML은 원 패키지로 노출됐고, 모든 `META-INF/versions/**`를 제거해 Jackson/jsoup/SnakeYAML 최적화 구현과 sqlite-jdbc native-image class를 버렸다. CI는 셸 helper, 실제 zero-match JAR 검사와 반복 package digest를 검증하지 않았으며 action·기본 lifecycle plugin 버전도 고정하지 않았다.
- **결정:** Apache Shade의 NOTICE transformer로 원 NOTICE를 `META-INF/NOTICE`에 병합하고 FastDoubleParser·Schubfach의 포함 라이선스와 SnakeYAML을 별도 저작물로 고지한다. Jackson·jsoup·SnakeYAML base package를 `io.flowscope.shaded`로 relocate하고 모든 MR-JAR class를 보존한다. Shade 3.6.0의 알려진 MSHADE-406 때문에 versioned bytecode의 ZIP entry path가 이동하지 않는 부분은 package 마지막의 결정론적 Ant 단계로 Java 9/11/17/21 경로까지 일치시킨다.
- **SQLite 경계:** `org.sqlite` relocate는 JNI symbol/package 계약을 깨뜨릴 수 있어 적용하지 않는다. 실제 sqlite-jdbc 3.53.1.0 JAR을 서로 다른 두 `URLClassLoader`에서 동시에 로드해 두 in-memory connection과 query가 성공하는 회귀를 둔다. 이 결과는 현재 의존성·JVM 조합의 알려진 충돌 주장을 반증하지만, 임의의 미래 Burp 확장 조합에서 충돌 확률이 수학적으로 0임을 보장하지는 않는다. 충돌이 재현되면 SQLite sidecar 또는 pure-Java 저장소를 별도 결정으로 검토한다.
- **빌드·CI:** `clean verify`가 쓰는 clean/resources/compiler/surefire/jar/shade/antrun plugin을 명시적으로 고정한다. GitHub Actions는 검증한 commit SHA에 pin하고 push는 main으로 한정한다. CI는 `find+mapfile`로 정확히 JAR 한 개를 확인하고, MR-JAR/NOTICE/라이선스/relocation 누출/manifest를 검사하며, Bash 5개에 `bash -n`·ShellCheck, PowerShell 4개에 parser gate, 같은 toolchain의 clean package 2회 SHA-256 일치를 요구한다.
- **기각:** 모든 `META-INF/versions/**` 삭제는 동작을 base class에 강등하고 native-image descriptor를 깨뜨려 기각했다. 모든 dependency를 동일하게 relocate하는 방식은 SQLite JNI에 안전하지 않아 기각했다. SQLite를 즉시 별도 프로세스로 분리하는 방식은 실제 충돌 재현 없이 설치·장애 표면을 늘리므로 현재는 기각한다. mutable action tag와 inherited plugin version은 동일 commit의 빌드 입력을 외부 상태에 맡기므로 유지하지 않는다.
- **근거:** [Apache License 2.0 §4(d)](https://www.apache.org/licenses/LICENSE-2.0), [Maven plugin version](https://maven.apache.org/guides/mini/guide-configuring-plugins.html)·[reproducible-build](https://maven.apache.org/guides/mini/guide-reproducible-builds.html) 가이드, [GitHub Actions secure-use SHA pin 지침](https://docs.github.com/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions), [Apache Maven Shade MSHADE-406](https://github.com/apache/maven-shade-plugin/issues/652). 로컬 검증은 NOTICE 병합, versioned entry/class load, 두 SQLite classloader, 반복 SHA-256, Bash 정적 검사를 포함한다.
- **상태:** beta.23 코드·로컬 자동/패키징 검증 완료. 원격 GitHub Actions와 실제 Burp 다중 확장 load/unload는 대기.

## D-091 · 판정 오라클과 동시 게시 = 자원 한정 ID + 오류 봉투 + 격리 스냅샷

- **문제:** 응답 객체 판독이 정확한 `id` 필드만 받아 `orderId/order_id/uuid/pk`를 놓쳤고, soft-deny 문구를 응답 전체에서 검색해 정상 목록 내부의 `status: not allowed`도 거부로 뒤집었다. 입력 JSON과 재귀 순회에 명시 상한이 없었고, 같은 응답을 읽는 소유자·DataFlow 경로도 각각 무제한 재귀와 정규식 검색을 수행했다. Burp worker는 이전 Web 게시본과 같은 가변 `RequestRecord`를 다음 재분석에서 다시 수정했고, 정책 맵도 개별 concurrent map이라 전체 교체의 중간 조합을 읽을 수 있었다.
- **객체 결정:** generic `id/uuid/guid/pk`와 **최종 자원 타입에 한정한** `*Id/*Uuid/*Guid/*Pk/*Number/*No/*Seq/*Key/*Ref/*Vin`만 같은 scalar 값일 때 객체 노출 근거로 인정한다. `orders:101/items:5`는 item 5만 대상이며 order 101만 보인 응답은 성공 근거가 아니다. 콜론 없는 잘못된 resource도 근거 없음이다.
- **거부 결정:** 401/403과 로그인 경로 redirect는 그대로 명시 거부다. 2xx soft-deny JSON은 최상위 `error/errors/message/detail/title/reason` 오류 봉투에서만 찾고 배열·도메인 데이터 내부 문자열은 검색하지 않는다. 비 JSON 오류 페이지만 앞 2,048자를 검사한다.
- **자원·동시성 결정:** 판독 입력은 1,000,000자, JSON 깊이 128, token·node 100,000으로 제한하고 객체·소유자·구조화 DataFlow 검색은 반복 순회한다. malformed/non-JSON DataFlow fallback은 앞 64KiB와 값 1,000개로 제한한다. 정책 일곱 맵은 단일 monitor 아래 교체·갱신하며 분석/직렬화는 한 시점의 정책 복사본을 쓴다. Burp/Web/MCP/Standalone 게시본은 수집 DTO의 분석 복사본으로 만들어 이후 callback·재분석과 공유하지 않는다. raw byte vault는 영속되지 않는 runtime ID로 두 복사본을 연결한다.
- **신원·키 결정:** 인증 지문 추출 실패 `unresolved`를 실제 무자격 `anon`과 분리하고 둘 다 계정 binding을 거부한다. service는 session bind/read/unbind 모두 `scheme://host:port`로 정규화한다. `UNKNOWN` 역할은 BFLA 정상 대조 권한으로 쓰지 않는다. Evidence digest 입력은 개행 join 대신 UTF-8 byte 길이 framing을 쓰되 beta.23 이하 digest를 감지해 기존 Evidence ID를 보존한다. cell은 일반 기존 stable key를 유지하고 `|` 또는 literal `<none>`이 포함된 위험 입력만 `v2` 길이+hex framing으로 전환해 기존 finding/review ID를 불필요하게 바꾸지 않는다.
- **리뷰 판별:** 비어 있는 지문과 `anon`의 생성자 경계 혼동은 유효했지만, “인식 못 한 비어 있지 않은 Authorization이 blank가 된다”는 설명은 현재 `Fingerprints.of` 경로와 맞지 않는다. 해당 값은 opaque token hash가 된다. `AccessRole.isBelow(UNKNOWN)==false`도 분석 후보를 함부로 위반으로 만들지 않는 의도된 동작이며, 실제 결함은 Judge의 BFLA 정상 대조 호출부가 이를 “권한 충분”으로 역해석한 지점이었다. unbind 뒤 stale `idn`은 기존 `Pipeline`의 정규화 재실행 경로에서 재현되지 않았으므로 생산 결함으로 확정하지 않고 직접 호출 경계만 재설정했다.
- **기각:** 중첩 자원의 모든 부모 ID를 대상 노출로 인정하면 자식 객체가 없는 응답도 BOLA 성공이 된다. `Gap.risk`와 finding `Severity` 통합은 후보 정렬값과 취약점 심각도를 혼동한다. 모든 `RequestRecord` 필드를 즉시 immutable record로 바꾸는 전면 API 파괴 대신, 실제 동시 게시 경계를 복사해 기존 parser/test 호출 계약을 유지한다.
- **한계:** 자원명이 필드명과 전혀 다르고 generic ID도 없는 응답은 계속 `UNDECIDED/INCONCLUSIVE`다. 오류 봉투가 아닌 서비스 고유 soft-deny는 자동 거부로 잡지 못할 수 있다. DataFlow의 substring 소비 판정과 전체 조합 O(N²), 내부 `RequestRecord`의 공개 가변 필드는 남아 있다. 다만 Burp/Web/MCP 게시본은 복사되어 실제 게시 경합에는 쓰이지 않는다. 이 한계는 false allow로 확정하지 않고 blind benchmark와 stress gate에서 측정한다.
- **상태:** beta.24 `mvn clean verify`에서 243개 자동 회귀, 실패·오류·skip 0. 실제 Burp/Judge 수동 gate는 별도 기록.

## D-092 · fat JAR 재구성 = streaming manifest + 버전 독립 MR 경로

- **문제:** D-090의 Ant 후처리는 일반 `<zip>`으로 staging 디렉터리를 다시 압축해 `META-INF/MANIFEST.MF`가 첫 엔트리에서 밀렸다. `JarFile`과 Burp 로딩 경로에서는 manifest와 Multi-Release가 보였지만 순차 입력인 `JarInputStream.getManifest()`는 `null`이었다. 또한 versioned relocation 대상이 Java 9/11/17/21 경로별로 고정돼, dependency가 새 version 디렉터리를 추가할 때 POM 수정이 필요했다.
- **결정:** 재구성은 원 manifest를 명시적으로 받는 Ant `<jar>`로 수행하고 staging의 manifest 중복 입력은 제외한다. JDK patch 문자열이 artifact를 바꾸지 않도록 `Created-By`도 고정한다. Jackson·jsoup·SnakeYAML versioned class는 `META-INF/versions/*/...` fileset과 정규식 mapper로 이동해 version 숫자를 빌드 로직에서 제거한다. `FatJarIsolationSmoke`를 Maven `verify` phase에 연결해 `JarInputStream`에서 manifest가 존재하고 Main-Class·Java-Version·Multi-Release 값이 정확한지, 실제 JDK가 relocated MR class를 선택하는지, SQLite 격리 연결이 성공하는지를 완성 JAR에 대해 검사한다.
- **검증:** beta.25 `mvn clean verify`에서 243개 자동 회귀와 완성 JAR smoke가 통과했다. JAR 첫 엔트리는 `META-INF/MANIFEST.MF`, 2회 clean package SHA-256은 일치했다. 기존 9/11/17/21 class가 wildcard mapper를 통해 이동하고 원 versioned package 누출이 없음을 확인했다.
- **한계:** 이 gate는 현재와 미래의 동일 package prefix 아래 version 디렉터리를 처리한다. dependency가 package 자체를 바꾸거나 새로운 relocate dependency를 추가하면 별도 설계 변경이 필요하다. 실제 Burp load/unload와 외부 SBOM·서명 도구 호환성은 자동 gate가 대신하지 않는다.
- **상태:** beta.25 코드·로컬 자동/패키징 검증 완료. 원격 GitHub Actions와 실제 Burp load/unload는 대기.

## D-093 · ZAP HAR 가져오기 = SCANNER HTTP Evidence 전용 폴백

- **문제:** beta.20~25 Web의 스캐너 파일 버튼은 이름과 달리 Burp XML만 받았다. ZAP에서 이미 수집·선택한 HTTP 메시지를 HAR로 내보낼 수 있지만 FlowScope에는 이를 SCANNER 레인으로 가져오는 어댑터가 없어, 사용자가 ZAP 결과를 다시 프록시하거나 XML로 변환해야 했다.
- **결정:** Web의 스캐너 입력만 `.xml,.har`를 허용한다. `.har`는 HAR 1.2 `log.entries[].request/response`의 method, absolute URL, query, headers, postData, status, response content, startedDateTime을 `SCANNER/HAR_IMPORT/ZAP/IMPORT/IMPORTED` RequestRecord로 변환한다. 인증값은 지문 계산 뒤 기존 Masking을 거치고, 파일 25MiB·JSON 깊이 128·token 1,000,000·전문 1MiB/압축 총량 48MiB 경계와 현재 exact scope를 적용한다. 잘못된 entry는 항목 단위로 건너뛰고 `status=0`은 응답 없는 후보로 둔다. base64 textual content는 엄격 UTF-8로 해석하며 binary/비정상 textual byte는 문자열로 치환하지 않고 metadata-only로 보존한다.
- **신뢰 경계:** HAR는 HTTP message archive다. FlowScope는 파일만으로 ZAP native Alert, Traditional/Client/AJAX 단계, passive queue 완료, 신원별 fresh session, controlled execution을 만들지 않는다. 따라서 HAR import는 SCANNER Evidence를 보충하지만 `COMPLETED` scanner lane이나 Judge의 ZAP Alert 입력을 충족하지 않는다.
- **기각:** HAR 안의 `creator.name`만 보고 임의 source를 바꾸는 방식은 조작 가능한 metadata를 provenance로 신뢰하므로 기각했다. HUMAN/LLM 업로드에도 HAR를 허용하는 방식은 현재 사용자 요구와 실제 export 경로보다 범위를 넓히고 source 오지정을 쉽게 만들어 기각했다. ZAP Alert JSON을 HAR에서 추론하는 방식은 형식에 없는 정보를 창작하므로 기각했다.
- **근거:** ZAP 공식 Import/Export 문서는 **Save Selected Entries as HAR**가 선택 HTTP message를 저장하고 `exportHar` API가 ZAP이 보낸 HTTP messages를 HAR로 반환한다고 설명한다. Alert는 별도의 ZAP core/ascan API 산출물이다. [ZAP Import/Export](https://www.zaproxy.org/docs/desktop/addons/import-export/), [ZAP API](https://www.zaproxy.org/docs/desktop/start/features/api/).
- **검증:** `HarParserTest`가 textual/base64/binary, response-less, malformed entry, exact-scope 경계를 확인하고 `FlowScopeWebServerTest`가 `.xml,.har` UI 계약, scanner-only API와 snapshot source를 확인한다. beta.26 `mvn clean verify` 249 tests와 완성 JAR smoke가 통과했다.
- **한계:** HAR request `postData.text`와 response `content.text`에 없는 원 byte는 복원할 수 없다. imported Evidence에는 Burp live raw-byte vault가 없으므로 Web 요청 실험실 원문 전송 대신 마스킹된 상세·Repeater 폴백 경계를 따른다. 실제 ZAP 2.17 UI에서 만든 HAR 파일의 Burp beta.26 수동 import는 별도 gate다.

## D-094 · ZAP 안전 기본 캠페인 = passive 전면 활성화 + 두 rendered crawler + Alert 전 페이지

- **Context 보정:** `scanOnlyInScope=true`만 켜고 Context를 만들지 않으면 ZAP 자체 scope가 비어 passive 미탐이 생길 수 있다. 신원별 session reset 직후 선택 target subtree 전용 Context를 생성·include·in-scope 처리하며, 이 중 하나라도 실패하면 spider 전에 lane을 실패시킨다.
- **Context 근거:** ZAP 공식 `passiveScan-config` 문서도 `scanOnlyInScope=true`인데 scope를 정의하지 않으면 passive Alert가 하나도 발생하지 않는다고 명시한다. [ZAP passiveScan-config](https://www.zaproxy.org/docs/desktop/addons/passive-scanner/job-pscanconf/)

- **결정:** 대상 트래픽 전에 ZAP version과 `spider/client/spiderAjax/pscan/pscanrules/selenium/openapi/websocket` add-on을 확인한다. 신원별 fresh session 안에서 passive engine과 전체 passive rule을 활성화하고 `scanOnlyInScope=true`로 설정한 뒤 Traditional, strict Client, AJAX를 모두 독립 실행한다. passive queue가 0이 된 뒤 `numberOfAlerts`와 500개 페이지를 사용해 신원별 최대 20,000개 Alert 상세를 고정 snapshot에 저장하며 초과는 경고한다. Client/AJAX 실패 또는 capture 0은 다른 Evidence를 버리지 않고 `COMPLETED_WITH_WARNINGS`로 노출한다. 로컬 CLI 자식 환경에는 해석된 실행 파일 부모를 `PATH` 앞에 추가하되 provider API key는 계속 제거한다.
- **기각:** Forced Browse는 ZAP 2.17 add-on에 자동화 API/Automation Framework job이 없고 사전 목록 전체를 GET해 대상 부하를 높이므로 안전 기본 버튼에 넣지 않는다. Active Scan·Fuzzer·Replacer·Sequence 변조도 passive가 아니므로 기존 별도 승인 경계를 유지한다. OpenAPI/GraphQL/SOAP/Postman URL을 이름만으로 추측해 자동 import하는 방식은 잘못된 endpoint 호출과 상태 변경 요청을 만들 수 있어 넣지 않는다. OpenAPI add-on은 in-scope 정의를 spider 중 자동 감지하므로 해당 안전 경로만 기본 사용한다.
- **근거:** ZAP 공식 Passive Scanner 문서는 passive scan이 ZAP이 생성·proxy한 요청/응답을 수정하지 않고 분석하며 API가 rule 활성화와 scope-only 설정을 제공한다고 명시한다. OpenAPI add-on은 in-scope 정의를 spider 중 자동 감지한다. ZAP API는 Alert pagination과 total count를 제공한다. Forced Browse 공식 문서는 wordlist 항목을 직접 요청하고 thread 수가 대상·로컬 부하를 높일 수 있다고 설명하며, 로컬 ZAP 2.17 API UI에도 Forced Browse component가 노출되지 않았다. 참고: [Passive Scanner](https://www.zaproxy.org/docs/desktop/addons/passive-scanner/), [Passive API](https://www.zaproxy.org/docs/desktop/addons/passive-scanner/api/), [OpenAPI Support](https://www.zaproxy.org/docs/desktop/addons/openapi-support/), [Forced Browse](https://www.zaproxy.org/docs/desktop/addons/forced-browse/), [Forced Browse options](https://www.zaproxy.org/docs/desktop/addons/forced-browse/options/).
- **검증:** mock ZAP 2.17에서 필수 add-on 누락 전송 차단, passive enable/all-rules/scope-only API parameter, Client와 AJAX 동시 capture, 501 Alert의 500+1 pagination·마스킹·snapshot paging, 세션별 fresh reset을 회귀로 고정한다. `LocalLlmRunnerTest`는 실행 파일 디렉터리 PATH 선두 추가와 중복 방지, 구독 환경 API key 제거를 검증한다. 실제 Burp 8081 capture와 provider 로그인 CLI 왕복은 beta.27 JAR 재로드 뒤 수동 gate다.

## D-095 · Explorer의 성공 조건은 CLI 종료가 아니라 응답 Evidence이며 ZAP 정의는 명시 입력만 확장한다

- **문제:** beta.27 Codex Explorer에서 안전한 GET도 destructive tool로 선언돼 승인 취소가 발생했고, 대상 응답이 0건이어도 모델이 `flowscope_end_run`을 호출하면 CLI exit 0과 함께 LLM lane이 완료될 수 있었다. `--ignore-user-config`는 `config.toml`만 제외하고 사용자 `SKILL.md`는 계속 system prompt에 포함하므로 전역 `ctf-goal`이 독립 Explorer에 섞였다. ZAP은 crawler와 OpenAPI 자동 감지는 갖췄지만, 공식 문서가 권장하는 이미 보유한 GraphQL·Postman·SOAP·OpenAPI 정의의 명시 import와 upstream fail-closed 검사가 없었다.

EXPLORATION 종료는 같은 run의 실제 응답 Evidence가 한 건 이상일 때만 허용한다. beta.28에서는 발견한 user/plugin skill 경로를 `enabled=false`로 주입하고 plugin/app/browser/computer-use/multi-agent feature를 비활성화하려 했다. 후속 실실행에서 이 skill 열거 방식만으로는 전역 skill이 빠지지 않음이 확인돼 Codex home 격리는 D-096으로 대체한다. ZAP은 outgoing proxy가 FlowScope scanner listener를 가리키는지 대상 전송 전에 확인한다. 운영자가 Web/MCP에 명시한 exact-scope 정의만 신원별 Context 안에서 최대 1,000 message로 import하고, 정의 실패는 다른 crawler Evidence를 폐기하지 않는 경고로 남긴다.
- **기각:** 단순히 프롬프트에 “스킬을 무시하라”고 쓰는 방식은 system prompt가 이미 주입된 뒤라 격리가 아니다. CLI exit 0만 성공으로 보는 방식과 0건 run을 강제 clear하는 방식은 빈 레인을 정상 데이터처럼 잠그게 하므로 기각했다. 잘 알려진 파일명이나 `/graphql`을 임의 probe해 정의를 찾는 방식은 서비스별 오탐·불필요 요청을 만들므로 기각했다. ZAP 전역 proxy를 FlowScope가 자동 덮어쓰는 방식은 기업 upstream 설정을 파괴할 수 있어 fail-closed 안내를 선택했다.
- **근거:** 로컬 Codex 0.147.0 help는 `--ignore-user-config`가 `$CODEX_HOME/config.toml`만 제외한다고 명시했고, 실제 `codex debug prompt-input`에서 beta.27 옵션과 beta.28 skill-disable 주입 모두 전역 `ctf-goal`을 계속 포함했다. 따라서 beta.28 문서의 제거 완료 주장은 잘못됐으며 D-096에서 정정한다. ZAP 공식 탐색 가이드는 modern app에서 Traditional+Client Spider와 API 정의 import 병행을 권장한다. OpenAPI 문서는 `importUrl(url, hostOverride, contextId, userId, maxMessages)`와 Context exclusion, 동기 경고, maxMessages soft limit을 설명하며 Network API는 outgoing HTTP proxy 조회·설정을 제공한다. [ZAP Exploring Your App](https://www.zaproxy.org/docs/getting-further/automation/exploring-your-app/), [OpenAPI Support](https://www.zaproxy.org/docs/desktop/addons/openapi-support/), [Network API](https://www.zaproxy.org/docs/desktop/addons/network/api/).
- **검증:** `McpServerTest`는 read/write tool method·annotation, 0-Evidence 종료 거부, explicit OpenAPI import와 lane count를 확인한다. beta.28의 `LocalLlmRunnerTest`는 skill-disable 인자 생성만 확인했으므로 실제 격리를 증명하지 못했다. `ZapClientTest`는 설치된 2.17 API parameter와 1~1,000 message bound를 확인하며 `FlowScopeWebServerParsingTest`는 네 형식의 compact 입력을 고정한다. 실제 Burp→Codex target read와 각 정의 형식의 실대상 import는 별도 통합 gate다.
- **한계:** provider가 CLI 내부 동작이나 config key 의미를 바꾸면 격리 smoke를 다시 수행해야 한다. FlowScope는 model 판단의 통계적 독립성을 증명하지 못하며 새 process·서버 격리·입력 차단을 보장한다. ZAP `maxMessages`는 redirect 때문에 soft limit이고, scope 외 redirect는 Burp 8081의 `ProxyScopeHandler`가 drop하지만 upstream이 잘못되면 캠페인 자체를 시작하지 않는다. 정의 import는 명세가 만들어 내는 요청의 업무 영향을 자동 판별하지 못해 별도 승인이 필요하며 Active Scan도 계속 독립 승인이다.
- **승인 보정:** 명세 import 자체가 POST·PUT·PATCH·DELETE 예제 요청을 만들 수 있으므로 정의가 하나라도 있으면 별도 Burp dialog 승인을 요구한다. 이를 단순 “비파괴 import”로 취급하지 않으며 승인 거부 시 fresh ZAP session과 대상 트래픽 전 단계에서 중단한다.

## D-096 · Codex Explorer 격리 = 로그인만 연결한 임시 CODEX_HOME + Evidence 이중 gate

- **문제:** beta.28 JAR의 실제 Codex Explorer 출력에서 전역 `ctf-goal` skill이 읽혔고, 모델이 첫 GET을 read tool 대신 destructive write tool로 호출해 client가 취소했다. 그 뒤 대상 응답 Evidence가 0건인데도 실행 중인 구버전 경로는 run을 닫고 UI를 성공으로 표시했다. 설정 파일 무시와 skill-disable 문자열만으로는 provider가 조립한 system prompt를 격리하지 못했다.
- **결정:** Codex 실행마다 owner-only 임시 `CODEX_HOME`을 만들고 원 사용자 홈의 `auth.json`만 링크한다. 원 `config.toml`, skills, plugins, memories와 sessions는 임시 home에 넣지 않는다. symbolic link가 불가능하면 hard link, 그것도 불가능하면 owner-only 임시 복사본을 쓰고 run workspace와 함께 삭제한다. 실행 인자에는 `--ignore-user-config`, `--ignore-rules`, `--ephemeral`, strict config와 skill/plugin/browser/shell 계열 feature disable을 유지한다. 활성 Explorer의 MCP `tools/list`는 역할에 필요한 8개로 제한하고 첫 target operation은 exact entry target의 `flowscope_target_read(method=GET)`로 고정한다.
- **성공 판정:** MCP `flowscope_end_run`은 같은 source/run/phase의 응답 Evidence가 없으면 context를 닫지 않는다. `LocalLlmRunner`도 CLI 종료 후 정확한 run ID의 Evidence를 다시 조회한다. 두 번째 검사에 실패하면 이미 생긴 LLM 완료 표식도 취소하고 `FAILED`로 게시한다. CLI exit 0이나 모델의 완료 문장은 성공 오라클이 아니다.
- **근거:** 로컬 Codex CLI 0.147.0의 `--ignore-user-config` help는 config 파일만 제외한다고 명시한다. 같은 로그인에서 일반 `CODEX_HOME`의 `debug prompt-input`은 전역 `ctf-goal`을 포함했지만, `auth.json`만 연결한 임시 home에서는 해당 지침이 사라졌다. 동일 격리 옵션을 적용한 실제 `codex exec --strict-config --ephemeral` 구독 실행은 `FLOWSCOPE_CODEX_OK`로 정상 종료했다. 이 smoke는 provider 로그인과 config 호환성만 증명하며 Burp MCP 대상 탐색 성능을 증명하지 않는다.
- **검증:** `LocalLlmRunnerTest`는 임시 home이 login만 노출하고 skill/plugin을 상속하지 않는지, login 부재 메시지, 격리 feature/ignore 인자, exact Evidence가 없는 완료의 실패 전환과 완료 lane 취소를 확인한다. `RunContextRegistryTest`는 launcher의 완료 취소를 고정하고 `McpServerTest`는 Explorer 8-tool 목록과 server-side 0-Evidence 종료 거부를 유지한다. 실제 beta.29 JAR의 Burp→Codex MCP target read·frontier 순회·정상 종료는 재로드 뒤 별도 gate다.
- **한계:** FlowScope는 provider binary 내부 구현이나 모델의 완전한 통계적 독립성을 증명하지 않는다. 로그인 파일 fallback copy가 사용된 플랫폼에서는 그 run 중 provider가 갱신한 인증 상태가 원 home으로 돌아가지 않으며 다음 실행에서 원 로그인을 다시 사용한다. Codex CLI가 feature/config 계약을 바꾸면 strict-config가 조용히 무시하지 않고 실행을 실패시키며 호환성 갱신이 필요하다.

## D-097 · Explorer 가시성 = 읽기 전용 활동 피드, Judge만 대화 재개

- **문제:** beta.29는 Web 버튼으로 구독 CLI를 시작했지만 실행 중 status는 한 문장이었고 output tail은 종료 실패 때만 보였다. 정상 실행이 오래 걸리면 사용자는 모델이 시작됐는지, MCP를 호출했는지, Evidence가 생겼는지 구분할 수 없었다. 반대로 CLI 원 JSONL·tool payload 전체를 그대로 노출하면 인증 header·응답 개인정보와 provider reasoning event가 화면에 섞인다.
- **결정:** provider JSONL을 bounded runtime event로 파싱해 `SYSTEM/MODEL/TOOL/EVIDENCE/ERROR`만 최대 200건 메모리에 유지하고 Web의 기존 1초 동기화로 표시한다. MODEL은 실제 provider message, TOOL은 도구명과 시작/완료만, EVIDENCE는 exact-run 완료 gate 결과만 보여 준다. reasoning/thinking event와 raw tool argument/result는 버린다. 전체 prompt는 운영 감사용으로 secret masking·24 KiB 상한 뒤 접힌 화면에 표시한다. Explorer는 자동 탐색이므로 입력창 없는 읽기 전용 피드이며, 후속 입력은 완료된 Judge session에만 허용한다.

- **검증:** `LocalLlmRunnerTest`가 실행 중 output 게시, Codex MODEL/TOOL event, reasoning·tool credential 비노출, prompt token 비포함과 Evidence gate event를 확인한다. `FlowScopeWebServerTest`는 작업 피드·provider message·prompt preview UI 계약을 확인한다. 실제 beta.30 Burp 재로드 뒤 provider 출력·MCP target Evidence·완료 전환을 확인하는 수동 gate는 남는다.

- **기각:** provider 홈 내부 파일을 Claude까지 추측하는 방식은 공급자 구현 세부사항에 결합돼 기각했다. polling마다 auth 명령을 실행하는 방식은 프로세스 폭증과 UI 지연 때문에 기각했다. FlowScope가 provider OAuth/API key를 직접 받는 방식은 구독 CLI 경계와 credential 책임을 바꾸므로 기각했다. 임의 디스크 전체 검색은 느리고 개인정보 경계를 넓히므로 표준 경로+명시 override로 제한했다.

## D-099 · 레인 완료와 잠금 = 목적별 trust 정책 + exact run Evidence 동결

- **문제:** 완료 판정이 HUMAN Web, MCP `end_run`, ZAP polling/baseline, 로컬 LLM launcher에 흩어져 있었다. 일부 ZAP 시작 실패 catch도 검증 없는 `clear()`를 호출했고, 완료 상태는 source 집합만 저장해 어느 run이 끝났는지 알 수 없었다. 8082 직접 프록시의 `UNVERIFIED_RUNTIME` 응답도 source/run/response만 맞으면 LLM 완료와 launcher Evidence gate를 통과했고, dataset lock은 완료 run이 아니라 같은 source의 과거 coverage와 결합될 수 있었다.
- **결정:** `SourceTrustPolicy`가 원 Evidence 보존, coverage, Explorer 가시성, 레인 완료, dataset lock, 최종 판정의 자격을 목적별로 판정한다. 8082 `UNVERIFIED_RUNTIME`은 보존하되 coverage·완료·잠금에서 격리한다. HUMAN 탐색은 `OBSERVED/CONTROLLED`, 시스템 SCANNER와 독립 LLM 탐색은 `CONTROLLED`만 완료 근거다. `LaneCompletionPolicy`는 활성 source·exact run ID·EXPLORATION·응답·trust를 한 번에 검사하며, 정상 완료 시 Evidence ID·응답 수·coverage 수를 `CompletedRun`으로 동결한다. 실패·취소는 `abort`만 사용한다.
- **잠금 결정:** `flowscope_lock_dataset`은 세 `CompletedRun`의 동결 Evidence ID가 현재 snapshot에 같은 source/run/phase/trust로 모두 존재하고 각 lane에 coverage Evidence가 있을 때만 성공한다. 잠금 입력은 이 동결 ID들로만 재구성하므로 같은 run ID의 후발 record나 imported/unverified record가 섞이지 않는다. 잠금 뒤 status도 live snapshot이 아니라 frozen snapshot을 읽는다.
- **영속 결정:** JSON project schema를 v3, SQLite storage schema를 v2로 올리고 exact `completed_runs`를 저장한다. JSON v1/v2와 SQLite v1은 읽되 source-only `completed_lanes`를 완료로 승격하지 않는다. 과거 프로젝트는 Evidence가 남아 있어도 세 레인을 다시 실행해야 한다. 불확실한 legacy run을 휴리스틱으로 추정하는 방식은 Judge 입력을 조용히 바꿀 수 있어 기각했다.
- **대체 범위:** D-054의 source-only 완료 저장·재잠금 설명을 이 결정이 대체한다. Explorer 시야 격리, active-run 차단, 별도 Judge와 validation Evidence 계약은 그대로 유지한다.
- **검증:** 무작위 run ID를 사용하는 no-cache 대조에서 동일 LLM 응답의 `CONTROLLED`만 완료 가능하고 `UNVERIFIED_RUNTIME`은 거부되는지 확인한다. HUMAN observed, SCANNER controlled, 실패 abort, completion Evidence 동결, 후발 same-run 대체 거부, lock 이후 live record 비가시성, JSON/SQLite exact-run 왕복과 legacy source-only 비승격을 자동 회귀로 고정한다.
- **한계:** 정책은 포트 사용자의 실제 OS 프로세스 신원을 증명하지 않는다. 특히 8081을 다른 로컬 프로세스가 오용하는 문제를 완전히 없애려면 ZAP adapter가 발급한 run-bound capability 또는 통제 채널이 추가로 필요하다. dataset lock 자체와 ZAP Alert/LLM prompt digest의 재시작 후 복원은 아직 별도 실행 정본 단계이며, 이번 결정은 완료 run membership의 무결성부터 고정한다.
- **상태:** beta.32 코드·JSON/SQLite migration·자동 회귀 완료. 실제 Burp 3-way run→저장→재열기→재잠금은 수동 통합 gate 대기.

## D-100 · 사용자 실행·분석 게시 무결성 = generation + idempotency + publication epoch

- **문제:** Request Lab이 전역 `eventId/service/editable`에 비동기 GET 결과를 바로 썼기 때문에 A를 연 뒤 B를 빠르게 열면 늦은 A 초안이 B 화면을 덮을 수 있었다. 전송 버튼만 비활성화했지만 인증 selector 변경 렌더가 다시 활성화해 POST/PUT/PATCH가 중복 실행될 수 있었다. 분석 worker도 record snapshot을 계산한 뒤 dataset 초기화나 새 validation이 발생해도 결과를 조건 없이 게시해 삭제한 데이터 부활·최신 결과 덮어쓰기가 가능했다. 매트릭스는 모든 빈 셀을 `crossgap`으로 꾸며 서버가 소유자 미확정으로 기각한 조합도 IDOR 후보처럼 설명했다.
- **결정:** Request Lab 초안은 화면을 열 때 증가하는 generation과 immutable Evidence ID를 함께 캡처하고 둘 중 하나가 달라진 응답을 폐기한다. 전송 중에는 Evidence 교체·편집·인증 모드·계정·닫기·Repeater·재전송을 하나의 in-flight 상태로 잠근다. 각 전송은 Web Crypto 난수 operation ID를 가지며 서버는 `Evidence ID/request/mode/account`를 길이 프레이밍 SHA-256으로 묶어 같은 ID·같은 입력은 한 번만 실행한다. 전송 결과를 받지 못한 동일 draft는 같은 탭 메모리의 operation ID를 재사용하고, 입력·Evidence가 바뀌면 새 작업으로 처리한다. 같은 ID의 다른 입력은 거부하고, 완료 cache에는 원문 요청·전체 응답 대신 compact 결과만 256건 유지한다.
- **분석 게시 결정:** 입력 변경 또는 즉시 분석마다 publication epoch를 증가시킨다. pipeline은 시작 epoch를 보존하고 결과 게시 시 같은 epoch인 경우에만 `latest`, route candidate, revision을 함께 바꾼다. 초기화·프로젝트 교체·새 validation·정책 변경 뒤 끝난 오래된 계산은 버린다. 전체 pipeline을 하나의 전역 lock에서 실행하는 방식은 Burp 응답 callback과 Web을 분석 시간만큼 막으므로 기각했다.
- **후보 표시 결정:** 빈 셀은 서버 `GapType.UNCROSSED`의 exact `(identity, operation, resource)` key와 일치할 때만 `미교차/IDOR 교차 후보`다. 나머지는 owner·applicability 근거가 없는 중립 `미검증`이며 gap 필터에도 포함하지 않는다. URL 이름이나 HTTP method만으로 빈 셀을 승격하지 않는다.
- **대안 검토:** `AbortController`만 쓰면 이미 완료 직전인 응답과 실제 전송의 서버 실행을 취소했다는 보장이 없어 generation 검사를 대체하지 못한다. 버튼 CSS/disabled만으로는 재전송 HTTP 요청을 막지 못해 서버 idempotency가 필요하다. 매 클릭마다 새 operation ID를 만들면 서버 실행 뒤 응답만 유실된 명시 재시도가 중복 상태 변경을 만들 수 있어, 응답을 전혀 받지 못한 동일 draft에만 키를 재사용한다. pipeline thread interrupt는 Jackson·정규화 단계의 즉시 중단을 보장하지 않아 결과 publish gate를 권위로 둔다.
- **검증:** `AnalysisPublicationGateTest`가 invalidation 뒤 stale publisher 거부와 current publisher 허용을 고정한다. `FlowScopeWebServerTest`가 동일 operation ID의 동일 요청은 실제 실행 1회, 다른 요청 충돌은 400, generation/in-flight/exact-candidate UI 계약을 확인한다. 이는 실제 브라우저 이벤트 루프와 Burp HTTP 왕복의 수동 지연 시험을 대체하지 않으며 beta.33 JAR 재로드 뒤 A→B 역전·selector 연타·clear/rebuild 경합을 별도 확인한다.
- **상태:** beta.33 코드·자동 회귀 구현. 실제 Burp 수동 지연·경합 gate 대기.

## D-101 · 대규모 관측 경계 = 선형 projection + bounded decode/restore/output

- **문제:** live record 상한이 20,000건이어도 반복 cluster의 전체 Evidence ID를 모든 event에 넣으면 단일 cluster에서 snapshot 크기가 O(N²)가 된다. DataFlow도 각 응답 값마다 모든 뒤 요청을 substring 검색해 시간은 O(N²), 의미는 `123`과 `1234`를 같은 전달로 오인했다. 1MiB를 넘겨 저장하지 않을 live 응답도 상한 판정 전에 전체 문자열·Jackson mask 복사본을 만들었고, 프로젝트 GZIP과 LLM assessment는 count 외 byte 예산이 없었다.
- **결정:** snapshot event는 cluster ID/count/time만 보내고 Evidence ID는 `/api/cluster-evidence` 200건 페이지로 분리한다. DataFlow는 시간순으로 신원+값 exact index를 만들고 path/query/request body의 token과 같을 때 가장 가까운 이전 producer 하나만 연결한다. index는 전역 최신 100,000 value를 넘으면 오래된 값부터 축출한다. live Montoya 메시지는 byte 길이를 먼저 확인하고 1MiB 초과 시 최대 64KiB만 decode·mask한다. raw vault는 요청 1MiB·응답 4MiB 초과 메시지의 배열을 받지 않고 실제 크기만 기록한다. 프로젝트 복원은 payload당 1MiB·서로 다른 평문 합계 48MiB, streaming GZIP 선언 크기 검증과 digest cache를 사용한다. assessment는 필드·배열·1,000건·4MiB 총량을 MCP와 persistence에 공통 적용한다.
- **의미 경계:** 상한 초과 live payload의 digest는 최대 64KiB 마스킹 표현·실제 크기·보존 사유를 식별하며 원문 전체 checksum이 아니다. DataFlow는 관측된 explicit token 재사용을 시각화할 뿐 인과관계, 축출된 오래된 값, 숨은 서버 state, URL encoding이나 의미적 동등성을 증명하지 않는다. 가장 가까운 producer 선택은 한 화면에 모든 과거 후보를 그려 발생하는 선 폭증을 막는 표시·근사 정책이다.
- **기각:** cluster ID 목록을 기본 snapshot에 압축해 계속 넣는 방식은 payload 크기만 줄이고 반복 복제를 남긴다. 대형 원문의 완전 digest를 위해 전체 raw를 Java 배열·문자열로 만드는 방식은 보호 목적과 충돌한다. GZIP `readAllBytes`, assessment count-only 제한, DataFlow substring 또는 모든 producer 연결은 입력이 허가된 대상에서 왔다는 이유만으로 JVM·그래프 비용을 신뢰하므로 기각했다.
- **검증:** `SnapshotJsonWriterScaleTest` 20,000건 직렬화, `DataFlowAnalyzerTest` exact-token 음성 대조·가장 가까운 producer·20,000건 index·100,000 value 축출, `BoundedHttpCaptureTest` 2MiB text/binary·동일 미리보기 크기 분리, `TransientExchangeVaultTest` metadata-only oversized 입력, `StoredPayloadTest` 선언 크기 초과 GZIP·metadata-only blob 거부, `ProjectStoreTest` 48MiB aggregate, `McpServerTest` assessment field/aggregate 경계를 고정한다. beta.34 전체 회귀는 연속 두 번 각각 293 tests, failure/error/skip 0이다.
- **성능·효과 판정:** 최종 연속 full `clean verify`의 snapshot stress는 0.912초·0.804초였다. 별도 Snapshot+DataFlow Maven 측정은 3.91초, 최대 RSS 378,273,792 bytes·peak memory footprint 176,901,248 bytes였지만 이는 Maven/JUnit JVM을 포함한 개발 머신 수치이며 Burp 상주 메모리로 일반화하지 않는다. 이 결정은 안정성과 substring 오연결을 닫았을 뿐 취약점 탐지 성능 향상을 증명하지 않는다. 정답 격리 benchmark에서 H, H+ZAP, H+ZAP+LLM, Judge의 고유 TP·FP·FN/INCONCLUSIVE·검토시간·자원 사용을 분리하고 기여 없는 레이어는 기본 경로에서 낮추거나 제거한다.
- **상태:** beta.34 코드·자동 회귀 완료. 실제 Burp 20,000건 polling/RSS와 블라인드 효능 비교는 대기.

## D-102 · Explorer 탐색 폭 = 독립 safe frontier 뒤 provenance-free assisted frontier

- **문제:** beta.34 Explorer는 첫 GET과 그 run의 응답에서 추출한 route만 볼 수 있고, 종료는 신뢰 가능한 응답 한 건이면 가능했다. 세션·scope·Evidence 경계는 안전했지만 entry 문서가 route를 거의 노출하지 않는 서비스에서는 `/manifest.json` 두 건 같은 결과로 끝날 수 있었다. 반대로 처음부터 HUMAN·SCANNER의 응답과 Evidence를 공개하면 3-way 독립 비교가 사라지고 Explorer가 기존 결과를 답습한다.
- **결정:** route frontier를 두 단계로 고정한다. `INDEPENDENT`는 현재 LLM run provenance만 보여주며 concrete GET/HEAD/OPTIONS와 concrete UNKNOWN(GET으로 실행)이 남으면 다음 단계 전환을 거부한다. 이 frontier가 소진되고 controlled response Evidence가 있을 때만 `ASSISTED`를 연다. ASSISTED는 다른 레인이 발견한 exact-scope service/method/path template만 blind hint로 주고 source, run ID, Evidence ID, adapter, 응답, 관측 성공 여부를 반환하지 않는다. 종료 시점에 두 단계 조회와 전체 최신 safe concrete frontier 0건을 서버가 다시 계산한다.
- **실행 경계:** 모든 safe read는 기존 Session Broker가 선택 계정의 현재 ACTIVE 인증을 주입하는 `flowscope_target_read`를 사용한다. POST/PUT/PATCH/DELETE는 자동 frontier 소진 대상이 아니며 기존 `confirmed=true`와 Burp 승인 없이는 실행되지 않는다. `{id}` 같은 동적 route는 현재 run에서 실제 값을 얻지 못하면 만들지 않고 미검증으로 보고한다. exact scope, redirect 비추적, 인증 원문 비노출 계약은 유지한다.
- **기각:** 전 레인의 전체 Evidence/응답을 Explorer에 즉시 공개하는 방식은 독립 측정을 오염시켜 기각했다. “가능한 경로를 모두 curl”하는 방식은 세션·scope·감사·승인 경계를 우회한다. route 수에 임의 최소값을 두는 방식은 작은 서비스에서 거짓 성과를 만들고 큰 서비스에서 미탐을 허용하므로 사용하지 않는다. 모든 동적 template와 write를 자동 실행하는 방식은 근거 없는 object ID 생성과 업무 상태 변경을 일으켜 기각했다.
- **한계:** 이 단계는 관측 HTML/폼/redirect/JavaScript literal/XML/manifest/API 정의에서 route를 추출하는 HTTP frontier다. 브라우저 JavaScript 실행, DOM 상호작용, SPA runtime network 관측은 아직 Explorer가 직접 수행하지 않으므로 별도 browser worker 없이는 해당 route를 놓칠 수 있다. ASSISTED 단계는 recall 보완 결과이지 독립 LLM coverage 수치에 합쳐 우월성을 주장할 근거가 아니다.
- **검증:** `McpServerTest`가 independent safe route 잔존 시 assisted/종료 거부, 소진 뒤 cross-lane hint의 provenance·Evidence 비노출, assisted safe route 잔존 시 종료 거부, 양쪽 소진 뒤 exact run 완료를 고정한다. 실제 Burp+허가 target에서 route recall이 증가하는지는 블라인드 benchmark 전까지 완료로 주장하지 않는다.
- **상태:** beta.35 코드와 `mvn clean verify` 294 tests·완성 JAR smoke 완료. 두 번째 재현 build와 실제 Burp Explorer는 후속 gate다.

## D-103 · 렌더링 탐색 = 설치된 Chrome CDP 작업기 + discovery/replay 신뢰 분리

- **문제:** HTTP 응답 문자열에서 route를 추출하는 D-102만으로는 JavaScript 실행 뒤 생성되는 SPA DOM, 버튼 전이, 런타임 fetch/XHR을 볼 수 없다. Playwright·Chrome MCP를 추가하면 Node/npm과 별도 package 설치가 사용자 환경에 새 필수조건이 되고, 일반 8082 프록시 트래픽을 곧바로 `CONTROLLED`로 승격하면 어떤 로컬 프로세스가 보냈는지 서버가 증명하지 못한다.
- **결정:** BOLA/BFLA/IDOR의 핵심은 계정·역할별 HTTP 요청/응답 대조이므로 Explorer는 `flowscope_target_read/request` API-first로 시작한다. 정적 HTTP frontier가 SPA shell·JavaScript 상태·UI-only workflow에서 막힐 때만 JDK 21의 `HttpClient/WebSocket`과 설치된 Chrome/Chromium/Edge CDP를 rendered-discovery fallback으로 사용한다. browser run은 incognito 비표준 임시 `--user-data-dir`와 임의 remote-debugging port를 만들고 `Page/Runtime/Network/Fetch` domain으로 bounded DOM, 링크·폼·버튼, 런타임 request URL/method/type/status를 관찰한다. `Fetch.requestPaused`에서 현재 exact scope 밖 요청은 `BlockedByClient`로 중단한다. 선택 account는 run 시작 시 고정하고 `SessionBroker`의 target별 header/cookie를 같은 scheme·host·effective port request에만 CDP로 주입한다. 여러 scope entry가 있어도 다른 service에는 이 header를 붙이지 않으며 Chrome persistent cookie DB를 사용하지 않는다. 종료·unload 때 프로세스와 임시 profile을 삭제한다.
- **신뢰 분리:** 브라우저 DOM/network와 8082 사본은 route 발견 힌트이며 Evidence ID를 만들거나 lane을 완료하지 않는다. 모델은 관련 GET/HEAD/OPTIONS를 `flowscope_target_read`, 상태 변경을 기존 이중 승인형 `flowscope_target_request`로 재현해야 `CONTROLLED` Evidence를 얻는다. CLICK/FILL은 `confirmed=true`와 Burp dialog를 요구하고 password/file input을 코드에서 차단한다. arbitrary JavaScript 실행 tool은 제공하지 않는다.
- **기각:** 기본 Chrome profile에 remote debugging을 붙이는 방식은 사용자 로그인·쿠키를 FlowScope run에 혼합한다. Chrome은 136부터 기본 data directory에 remote-debugging switch를 허용하지 않고 비표준 user-data-dir을 요구하므로 기술적으로도 맞지 않는다. 브라우저 request에 비밀 marker header를 붙여 proxy에서 신뢰하는 방식은 CORS/preflight와 대상 동작을 바꾸며 marker 유출·모방을 새 신뢰 문제로 만든다. CDP 관측만으로 최종 Evidence를 만드는 방식도 Burp 통제 executor의 동일한 scope·session·저장 계약을 우회하므로 기각했다.
- **근거:** Chrome 공식 문서는 CDP `Page.navigate`, `Runtime.evaluate`, `Network` events, `Fetch.requestPaused/continueRequest/failRequest`를 프로그램 제어면으로 제공한다. Chrome 136 보안 변경은 remote debugging에 비표준 user-data-dir을 요구하고 실제 profile과의 격리를 권고한다. [Chrome remote debugging 보안 변경](https://developer.chrome.com/blog/remote-debugging-port), [CDP Page](https://chromedevtools.github.io/devtools-protocol/tot/Page/), [CDP Runtime](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/), [CDP Network](https://chromedevtools.github.io/devtools-protocol/tot/Network/), [CDP Fetch](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/).
- **검증·한계:** `ControlledBrowserExplorerTest`는 로컬 설치 Chrome을 headless 임시 profile로 두 local HTTP service에 실제 연결해 CDP, exact-scope DOM/네트워크, 범위 밖 링크 제거, click 이동, 범위 밖 navigate 거부, 선택 service session header 수신과 다른 service 비누출, query secret 출력 마스킹, 종료를 확인한다. `McpServerTest`는 Explorer-only tool surface와 `DISCOVERY_ONLY`/Evidence ID 부재를 고정하고, `LocalLlmRunnerTest`는 CLI가 실패해도 exact run browser cleanup이 호출됨을 확인한다. 전체 `mvn clean verify` 296 tests와 완성 JAR smoke가 통과했다. 이 smoke는 local HTTP와 proxy 없는 작업기 핵심을 검증하며, beta.36 JAR을 Burp에 재로드한 HTTPS target·broker session·8082 proxy 왕복과 SPA endpoint recall 증가는 별도 통합/benchmark gate다. 브라우저 엔진 설치는 필요하지만 Playwright·Chrome MCP·ChromeDriver는 필요 없다.

## D-104 · 그래프 정본 = Evidence Fact Core + 계층형 투영, browser write는 요청 단위 승인

- **문제:** 기존 화면은 `identity → object → operation`을 한 번에 그려 객체 인스턴스가 많을 때 선이 교차했고, API 자체를 먼저 읽기 어려웠다. 또한 browser CLICK/FILL selector를 승인해도 그 동작이 실제로 어떤 POST·DELETE를 만드는지 승인 시점에는 알 수 없었다. browser worker가 선택형 8082 listener를 강제로 사용하면 listener가 없는 정상 설치에서 렌더링 fallback이 실패했다. runtime network route는 모델 출력에만 있어 Explorer 완료 frontier가 재현을 강제하지 못했고, target tool의 `account_id`가 활성 Explorer 계정을 바꿀 여지도 있었다.
- **결정:** coverage 대상 각 관측을 `GraphObservationFact`로 투영해 `Evidence × Identity × Service × API × Object × Source × Run × Phase × HTTP outcome`을 보존한다. 화면은 ① Target→표시용 API Group, ② Identity→API, ③ 선택 API의 Identity→API→Object 순서로 내려간다. API Group은 경로 segment 근거의 탐색용 분류이며 분석 key가 아니다. Object는 family로 먼저 접고 인스턴스를 선택적으로 펼치며, 접기·중복 표시 집계가 원 Evidence나 판정 cell을 변경하지 않는다. 이는 D-010의 열 순서와 단순 18개 객체 나열만 대체하고 그래프+매트릭스 병행 원칙은 유지한다.
- **실행 결정:** browser worker는 CDP exact-scope 차단과 broker header 주입을 직접 수행하므로 8082 listener에 의존하지 않는다. 안전 메서드는 탐색을 허용하고, 실제 POST/PUT/PATCH/DELETE request가 `Fetch.requestPaused`에 도달했을 때 메서드·마스킹 URL·마스킹 body preview를 운영자에게 보여 준 뒤 그 request 하나만 승인한다. selector 사전 승인은 권위가 아니며 비밀번호·파일 입력 차단은 유지한다. Explorer run의 계정은 시작 시 고정하고 다른 `account_id` override를 서버가 거부한다. browser runtime route는 `BROWSER_RUNTIME` discovery artifact로 frontier에 넣되 `evidence_backed=false`로 표시하고 controlled HTTP replay 전에는 완료할 수 없다.
- **기각:** 객체를 영구 제거하면 BOLA 비교 근거가 사라지고, 모든 인스턴스를 기본 표시하면 고카디널리티 객체에서 다시 털뭉치가 된다. URL 명칭을 LLM 의미 분류로 확정하면 도메인별 오탐과 비결정성이 생기므로 첫 단계는 근거가 명시된 path group만 쓴다. 클릭 전에 selector만 승인하는 방식은 실제 network side effect와 승인이 결합되지 않아 기각했다. browser route를 곧바로 Evidence로 승격하는 방식도 응답 저장·재현 계약을 우회하므로 기각했다.
- **검증·한계:** `GraphObservationFactTest`가 정규화 operation·object family·API group 근거·request-only/HTTP outcome을 고정한다. `ControlledBrowserExplorerTest`는 실제 headless Chrome이 만든 POST를 요청 단위 승인 거부 시 대상 서버에 보내지 않음을 확인한다. `McpServerTest`는 Explorer account override 거부와 browser-discovered frontier의 `evidence_backed=false`를 확인한다. UI JavaScript parse와 Web 계약 자동 회귀는 수행하지만 beta.37 JAR의 실제 Burp 화면·고카디널리티 데이터 가독성 및 endpoint/finding 효능은 별도 수동·블라인드 gate다. Path group은 업무 의미를 증명하지 않으며 향후 OpenAPI tag·GraphQL operation·사용자 주석 등 명시 근거가 있을 때만 보강한다.
- **상태:** beta.37 코드, inline JavaScript parse, 전체 verify 299 tests 연속 2회와 재현 JAR 완료. 실제 Burp 재로드·고카디널리티 화면·블라인드 효능 gate 대기.

## D-105 · 신원별 ZAP 직렬 실행은 유지하고 실행 관측 가능성을 계약으로 제공

- **문제:** 비로그인과 계정 lane은 세션·cookie jar 오염을 막기 위해 직렬 실행하지만, 먼저 실행되는 AJAX Spider가 수분 동안 `running`이면 후속 계정은 수집 0건 `PENDING`만 보여 정지·오류·정상 대기를 구분할 수 없었다. 서버는 Traditional 15분, Client/AJAX 각 20분, passive queue 5분 timeout을 이미 적용했지만 UI와 상태 API가 이를 숨겼다.
- **결정:** campaign, lane, stage 시작·종료 시각과 단계 timeout, 마지막 ZAP status heartbeat, 마지막 raw capture 또는 status 변화, ZAP 상태 원문을 current-process memory에서 추적한다. Web/API는 전체·lane·stage 경과초, 제한초, heartbeat/progress age, queue position/total과 현재 lane 완료 후 시작한다는 이유를 반환한다. 첫 lane이 ZAP session/context를 준비하는 동안은 `STARTING`, status heartbeat 10초 초과는 `NO_HEARTBEAT`, heartbeat는 정상이나 capture/status 변화가 30초 넘으면 `RESPONDING_NO_NEW_TRAFFIC`, deadline 초과는 `DEADLINE_EXCEEDED`로 분리한다. API 정의 단계 제한은 실제 HTTP timeout에 맞춰 정의 한 건당 2분으로 계산한다.
- **기각:** 계정 lane을 병렬화하면 ZAP 자원 경합뿐 아니라 proxy run context와 fresh session 전환이 겹쳐 source/identity 귀속을 오염시킨다. 새 트래픽 30초 부재를 자동 실패로 처리하면 SPA 안정화·passive queue·긴 client crawl의 정상 정지를 오판한다. 따라서 직렬 격리는 유지하고 관측 상태만 명시한다.
- **검증·한계:** MCP 회귀는 campaign timestamp, queue 순번·이유, lane timing/heartbeat 필드를 확인하고 Web 회귀는 elapsed/heartbeat/wait/activity 계약을 고정한다. heartbeat는 ZAP API 응답 생존성이고 crawler 내부 thread의 완전한 건강 증명은 아니다. 실제 장시간 AJAX Spider에서 시간 표시와 timeout 전환은 beta.38 Burp 재로드 gate다.
- **상태:** 코드, inline JavaScript parse, 전체 verify 299 tests 연속 2회와 재현 beta.38 JAR 완료. 실제 Burp 재로드·장시간 AJAX→후속 계정 전환·timeout 표시는 대기.
